# The Loadstone handbook

Canonical source: `handbook/pages/welcome.md`

Your next playthrough starts with a setup you can understand. This handbook explains how to install, inspect, maintain and create Loadstone setups, with the same source documentation used by the project itself.

Loadstone is a Windows developer preview built with Svelte and Electron. Native installation, source verification, recovery and library tools are implemented. Complete featured packages and 1.0 release acceptance are still in progress. A successful file check or a game reaching its menu is not a completed gameplay test.

## Choose your path

- **Players:** begin with [Your first setup](quick-start.md), then [install a native setup](../../docs/native-guided-install.md). Learn what review screens mean before admitting a candidate to your library.
- **Creators:** follow the [creator workflow](creator-workflow.md), starting with the installed version as evidence and tracing every required file to a reproducible source.
- **Contributors:** read the [development guide](development.md), [contribution rules](../../CONTRIBUTING.md) and [agent guide](../../AGENTS.md). Behavior and documentation should change together.

## Game support direction

| Game | Direction | What this means today |
| --- | --- | --- |
| Fallout: New Vegas | Primary support target | Native workflows are implemented; each setup still needs its own acceptance. |
| Fallout 3 | Through Tale of Two Wastelands | Standalone Fallout 3 is outside the supported direction. TTW requires the appropriate owned source games. |
| Fallout 4 | In development | Do not infer a tested setup from game detection or an example catalog entry. |
| Skyrim | In development | Source/edition requirements must be declared by the setup. |
| Starfield | Planned | Currently unsupported. |

## Three different things to verify

**Source identity:** the archive or owned-game file is exactly the version a recipe requests. **Reconstruction:** the resulting files and declared timestamps match the recipe. **Playable acceptance:** that particular game, profile and application version actually launch, play, save and reload correctly. Each answers a different question.

This is a local, searchable handbook. The pages are compiled from an explicit list of repository Markdown files; they are not fetched from a hosted service. Search includes page text. Source links lead to the matching public repository file. The complete Markdown agent edition is available from the navigation footer. Historical pages live in Archive and describe their own versions.

For current release gates, use [Path to 1.0](../../docs/1.0-plan.md). For definitions, use the [glossary](glossary.md). For a failed operation, start with [troubleshooting](troubleshooting.md).

# Your first setup

Canonical source: `handbook/pages/quick-start.md`

Start with a trusted `.loadstone` package and the source games and files it declares. The current app is a developer preview; there is no generally accepted featured catalog ready to promise a one-click playable result.

## Before you open a package

Use Windows and keep your existing playthrough intact. Check the setup's game edition, prerequisites, storage needs and save guidance. Choose a new destination with room for the completed installation and any temporary archive work. A package containing a recipe does not automatically contain the mods or game files it references.

If building the app from source, follow [development setup](development.md). An existing portable preview can be run directly, but its included feature set is determined by its recorded build revision.

## Install and review

1. Choose **Set up real installations** on first run. If you explored the demo, disable **Use dummy data** in Settings when ready for real work.
2. In Discover, choose **Open .loadstone**. Read the package identity, declared requirements and save guidance.
3. Select the owned game folders, original archives and prepared prerequisites requested by the guide. Use [manual Nexus downloads](../../docs/native-manual-downloads.md) or the available [source download workflow](../../docs/native-downloads.md) when applicable.
4. Choose a separate destination and review the plan. Fix missing or mismatched inputs before starting.
5. Follow the job in Downloads. Cancellation retains evidence for [reviewed resume](../../docs/native-build-recovery.md); do not manually mix files from different attempts.
6. After final verification, review the completed candidate and explicitly add it to My library. A completed job is not automatically admitted or certified playable.
7. Review the [launch requirements and shortcut options](../../docs/native-library.md). Use a disposable new game for first acceptance where the setup's save guidance requires it.

## What if I only want to look around?

Choose **Explore the demo**. Its fictional setups, downloads, validation and launch sessions are simulated. Demo mode does not prove that a real modlist will install. Your demo preferences are separate from native candidate files.

## What happens next?

Use library verification to detect file differences. [Repair](../../docs/native-repair.md) can restore missing or damaged recipe files while preserving local changes by default. [Install another version](../../docs/native-updates.md) builds a separate candidate. [Removal](../../docs/native-maintenance.md) reviews what can be removed and retains protected content.

Do not copy an old save into a new setup merely because both use the same game. Follow the specific setup's compatibility guidance and verify a disposable save/reload first.

# How Loadstone works

Canonical source: `handbook/pages/concepts.md`

Loadstone brings source selection, reconstruction, verification and a playable library into one desktop workflow. The app keeps these steps explicit so a failed download, a locally edited file and an untested game launch are not mistaken for the same problem.

## Native packages and external manifests

A **native `.loadstone` package** uses Loadstone's documented experimental recipe format. Its actions are typed file operations, with declared sizes and hashes. It can refer to original downloads, owned games and prepared prerequisites, and may include permitted payloads. See the [format reference](../../docs/loadstone-format.md).

A **live catalog manifest** belongs to the separate external-engine path. Wabbajack integration prepares and runs a verified external runtime; it does not turn any file with a familiar extension into a supported native package. See [manifest requirements](../../docs/manifests.md) and the [runtime guide](../../docs/runtime.md).

## From source to library

**Sources → reviewed plan → candidate → verification → admission → launch.**

Sources are locked inputs. A plan checks prerequisites and a separate destination. The builder creates a candidate and checks every required output. Admission reviews that completed candidate before creating a library entry. Launch uses its declared manager/profile configuration. Desktop and Steam shortcuts are explicit operations associated with that setup.

## Exact bytes and local state

A SHA-256 fingerprint plus a byte count identifies the expected file content. Some outputs also require a declared modification time, because game tooling may use timestamps for ordering. File verification does not compare visual similarity or assume that a newer mod download is interchangeable with the pinned original.

Save files, user settings and unexpected files are a different kind of state. Maintenance must preserve them according to the reviewed operation. Restoring recipe configuration is a separate repair choice because it can replace deliberate local settings.

## Sources inside sources

A loose file can originate inside a BSA container inside an original ZIP, 7z or RAR download. Native BSA reconstruction records every link in that chain. The [creator mapper](../../docs/bsa-inspection.md#nested-source-mapping) checks those links before recording a match. Arbitrary nested installers and generated transformations are not implied by BSA support.

## Evidence and permission

An installed inventory says what is present. A source match says where the exact bytes can be obtained. A recipe says how to produce the output. A rights review says what can be distributed. Acceptance says whether the result works in the intended environment. None of these replaces the others.

# Troubleshooting

Canonical source: `handbook/pages/troubleshooting.md`

Begin with the operation that failed, its exact setup version and the build identity shown by the app. Preserve the failed candidate and recovery folders while investigating. Export the app's diagnostic summary when useful; inspect it before sharing and keep raw logs, private paths and account credentials private.

## A source file does not match

Check that it is the original archive and version requested by the recipe. An extracted folder, a renamed replacement or a newer upstream release is not an exact substitute. The filename is only a lead; the byte count and SHA-256 are decisive. Use the guide's verification and cancellation controls instead of bypassing the mismatch. Creators should update a recipe only after reviewing the new source and resulting outputs.

## Nexus downloads are unavailable

Check the account state and last verification in Settings. Automatic downloads require the declared access conditions, including fresh Premium verification where required. [Manual downloads](../../docs/native-manual-downloads.md) open the declared Nexus file page for normal browser interaction, then validate the selected original locally. A missing or removed upstream file remains a source problem; the app does not invent a mirror or bypass website controls.

## The build was interrupted

Use the [resume review](../../docs/native-build-recovery.md). Matching files can be reused, while conflicting files are retained before reconstruction. A receipt is not proof that a partially written directory is complete. For a registered setup with an interrupted repair, follow the fresh repair review before trying to launch.

## Verification reports differences

Distinguish an intentional configuration edit from a missing or damaged static output. [Same-version repair](../../docs/native-repair.md) preserves existing profiles/configuration by default and keeps replaced originals. Choose configuration restoration only when you intend to return to recipe settings. If a source no longer verifies, repair cannot safely replace it with another version.

## Steam is running when I create a shortcut

Follow the app's running-client safeguard and close Steam normally before retrying a shortcut write. Steam can rewrite its shortcut database while running. Shortcut creation is separate from launching a game or proving its Steam startup requirements. See [library and shortcut guidance](../../docs/native-library.md).

## Steam load error or a game that will not start

Check the recipe's owned edition, game folder, manager executable, profile and declared Steam app ID. The [Steam startup notes](../../docs/native-library.md#steam-game-startup) record a case resolved after a normal Steam restart. Do not treat repeated automated menu input as a gameplay test. Once launch works, use an appropriate disposable new game and verify save/reload separately.

## A container cannot be inspected

Confirm that the selected trusted archive tool is supported and that the original is complete. BSA inspection currently accepts a bounded subset of version 104. A rejected variant is not necessarily a corrupt game archive. Review [archive comparison limits](../../docs/installed-inventory.md) and [BSA limits](../../docs/bsa-inspection.md). Keep an unresolved issue explicit; do not accept partial matches from an unsafe container.

## Removal retained a folder

This can be expected. Saves, configuration, modified files and untracked content may remain in recovery. Read the removal review and [recovery rules](../../docs/native-maintenance.md) before deleting anything manually. A retained folder is not a reason to retry a recursive deletion.

## Reporting a problem

Include the Loadstone build/version, Windows version, operation, setup identity and the smallest reproducible sequence. Use synthetic inputs for a public reproduction where possible. Follow [security reporting](../../SECURITY.md) for sensitive findings and [privacy guidance](../../docs/privacy.md) for diagnostic exports.

# Install a native setup

Canonical source: `docs/native-guided-install.md`

In the live workspace, **Discover → Open .loadstone** imports a native package and guides the player through its required inputs. A private-inputs JSON file is no longer required for this desktop path. The creator workflow in Settings and the local-only CLI remain available.

1. Review the package name, version, creator and save guidance. Loadstone validates the complete package before displaying the setup.
2. Select each required owned game. One detected Steam installation matching the declared game and store is selected automatically; ambiguous results require a choice. Detected folders are suggestions, and required file hashes are checked during installation. Fallout 3 for TTW and GOG installations currently require manual folder selection.
3. Select any prepared prerequisite folders. These may contain locally converted content; Loadstone checks the declared files and never runs prerequisite instructions or a converter.
4. For each archive, keep **Download from original source** or choose and verify an existing original archive. Sources are searchable and paginated. Automatic uncached Nexus downloads require a connected Premium account. [Browser-download mode](native-manual-downloads.md), the default without a known Premium connection, opens the exact Nexus file page and requires verified local selections before review. The player controls the website download; the app checks the selected file's size and SHA-256 with cancellable progress. Existing cache files can also be explicitly verified and selected. Automatic cache reuse follows the same [download rules](native-downloads.md).
5. Choose an existing installation parent, then **Review installation**. The app chooses a new child folder and shows the destination, output/storage counts, original download hosts, cache and archive reader. Select a trusted local 7-Zip x64 26.04 or newer when prompted for downloads or 7z/RAR inputs.
6. Confirm **Install native setup**. Downloads shows acquisition, source checks, reconstruction and final verification, with cancellation and persistent history. Starting from this screen uses the same [native builder](native-reconstruction.md) and output checks as the creator workflow.
7. After **Files verified · Launch untested**, choose **Review for My library**. Loadstone verifies that exact job destination and its portable MO2 launch layout again, then asks whether to add it. Cancellation adds nothing. Acceptance opens My library, where launch and optional Desktop/Steam shortcut controls are available. This step starts no game, imports no saves and creates no shortcuts automatically.

Packages without the required portable MO2 layout can reconstruct files but cannot pass library admission. A recipe's declared save compatibility is creator guidance, not a gameplay certification. Complete source permissions, clean-machine/provider acceptance and real game/save/client checks remain release gates.

**My library → Install another version** uses this flow for a [separate version update](native-updates.md). The original setup stays in its folder with its existing saves, settings and shortcuts; the selected version gets fresh recipe settings and a separate library admission.

## Recovery and privacy

For a cancelled, failed or interrupted installation, **Downloads → Review resume** asks for the same package and returns to the guided selections. Reselect local inputs; the installation parent is fixed to the original job. Review shows matching, missing and conflicting files and the recovery folder, with cancellable retained-file checking. Confirmation uses the existing [build recovery](native-build-recovery.md), retaining conflicts and reusing matching outputs under the same history record and destination.

Selected game, prerequisite and archive paths appear locally in the renderer so the player can review them. The private map and package path stay in the main process; no raw path map is accepted from renderer IPC. Detected folders use opaque per-import identifiers, and every selection is restricted to inputs declared by the recipe. Selection changes invalidate a reviewed plan. Import cancellation preserves the current selections but requires a fresh review.

The draft survives navigation while Loadstone remains open and is discarded on restart. It is not saved to history or diagnostic exports. Builds retain their existing destination/progress/history records, and source inputs must be selected again for recovery. Opening or reviewing a package does not download archives. Starting an installation explicitly allows its reviewed original-source acquisition; credentials retain the existing Nexus isolation.

## Verification

Service tests exercise required selections, ambiguous detection, invalid/stale identifiers, redirected folders, recipe replacement, concurrent selection rejection, cancellation/restart/resume, and local/downloaded archive paths through the shared builder. An actual Electron test exercises Discover import without JSON, Downloads cancellation/resume, explicit library admission cancellation/confirmation and restart persistence. All test game/tool bytes and provider responses are synthetic; no fixture executable is run and no real Desktop or Steam library is written.

# Source downloads

Canonical source: `docs/native-downloads.md`

The experimental desktop native builder can acquire `https-archive` and `nexus-archive` sources from a reviewed `.loadstone` package. [Guided installation](native-guided-install.md) defaults each archive to its original download and offers a native picker for manually downloaded originals. The creator workflow uses a private input map with either an absolute local archive path or `null` for each archive source ID:

```json
{
  "games": { "fnv": "C:/OwnedGames/Fallout New Vegas" },
  "archives": { "original-mod": null, "manual-mod": "C:/ModDownloads/manual.zip" }
}
```

The source IDs, lengths, hashes and public source references come from the recipe. The private map cannot substitute download URLs, credentials or executables. Games and local prerequisites still require prepared local folders. The CLI remains local-only.

## Review and execution

Both guided Discover review and creator Settings review show the archive count, maximum acquisition bytes, original source hostnames, local cache directory and selected archive tool before confirmation. No downloads occur during selection or package inspection. Starting re-inspects the package and rejects a changed recipe before network work. The materializer checks the same recipe fingerprint again before creating candidate outputs.

The builder acquires archives sequentially, then runs the existing complete input, archive-structure, write and final-file verification. Archive signatures select the actual parser. Acquisition is a separate progress phase; current-file bytes represent downloaded bytes or bytes rehashed from cache. Cancellation and the app close guard include acquisition.

The tool picker is required when any download is requested because its archive type has not yet been inspected. ZIP downloads use the built-in reader; 7z/RAR use the explicitly selected and fingerprinted local tool. No external tool is downloaded automatically.

## Cache and retry

The cache is `native-downloads/` beneath Loadstone's app-data directory. Completed archives use their SHA-256 as the filename. Each new download streams through an exclusive random `.part` file, enforcing the recipe byte length and hash before exclusive publication into the cache. A conflicting cache file is not replaced. Existing archives are rehashed before reuse; mismatches fail and preserve the file for inspection.

The builder checks for the expected archive bytes plus a 64 MB free-space reserve before each download. Archives remain bounded to 50 GB. Connections have a 30-second header/idle timeout and an acquisition attempt has a two-hour deadline. There is no automatic network retry or concurrent transfer. These are current creator-tool limits, not throughput promises.

Cancellation or a handled error removes only the current owned temporary download when its directory/file identity still matches. Verified archives remain for retry. A process kill can leave an orphan `.part` file; it is never treated as verified. Retrying reuses verified cached archives but restarts incomplete downloads from byte zero. The desktop can [review and resume a partial candidate](native-build-recovery.md), reusing matching output files and retaining conflicting files before reconstruction. Byte-range download resume, cache management and global cache quotas remain unfinished.

## Network and account handling

Original HTTPS downloads use port 443, normal TLS certificate/hostname validation and no cookies, browser session, proxy credentials or inherited authorization headers. Redirects are limited to five and each destination is revalidated. Local, private, link-local, multicast, documentation and other reserved IP ranges are rejected, including mixed public/private DNS answers. IPv6 is conservatively limited to global unicast excluding special ranges. The connection is pinned to a checked DNS answer while retaining the original hostname for TLS validation. This intentionally rejects some specialized networks; it does not add an unrestricted network proxy.

For an uncached Nexus source, the builder freshly verifies the locally protected account and requires Premium. It calls the specific game/mod/file download-link API, identifying Loadstone and its version. API redirects are refused. The key goes only to the fixed Nexus API origin; the returned HTTPS download link is used in memory without API headers, then discarded. Link responses are bounded to 128 KB. Free users can use [guided manual downloads](native-manual-downloads.md): open the declared Nexus file page, download in the browser and choose the archive for immediate verification. Browser mode requires verified selections before review; NXM protocol handling remains unfinished. A verified local cache hit requires neither a key nor an API request.

Public application registration and real-account download acceptance are still required.

# Library, launch & shortcuts

Canonical source: `docs/native-library.md`

In the live workspace, **My library → Add native candidate** selects a completed reconstruction folder, including a candidate built by the CLI. Keep MO2 and the game closed while reviewing or verifying it. Loadstone reads its recipe and reconstruction receipt, verifies every static output against its byte count and SHA-256, and checks the generated portable MO2 configuration. Progress is measured in recipe outputs; verification can be cancelled without changing candidate files.

The review shows the selected folder, profile, output count and the recipe author's save guidance. **Add to library** registers that reviewed candidate without starting a process or creating shortcuts. Only register a creator's executable content if you trust it: recipe fingerprints establish consistency, not safety or authorship. Reconstruction and file verification do not certify gameplay. The existing build history remains separate, and completing a build does not automatically register it.

## Admission and launch checks

- The recipe fingerprint must match a completed `verified` receipt. Its generated configuration fingerprint must match the selected destination. Copied candidates need a fresh reconstruction for their new paths.
- The current implementation requires the native `mo2-config` generator, an empty portable marker, the declared profile, and an isolated game directory. Static imported manager configuration is not supported for registration.
- MO2's base, mods, downloads, profiles, overwrite and cache paths must stay in their declared local directories. The selected launch entry must retain its declared title, binary, working directory and arguments. Duplicate INI sections/keys (including case variants), percent-encoded section/key names and ambiguous launch titles are rejected. MO2 may change unrelated window/UI values in supported sections.
- The selected profile's `settings.ini` must explicitly declare `[General]` `LocalSaves=true` and `LocalSettings=true`. Global defaults alone are insufficient. An existing local saves directory must not be redirected. Loadstone never imports an existing playthrough.
- The manager, selected launch executable and base game executable must match recipe hashes and have Windows executable headers. Directories and checked files must be ordinary, unredirected paths. Registration retains the root directory's identity, so replacement or redirection is rejected.

**Launch native setup** repeats the recipe/receipt, executable, path and local-profile checks before opening MO2 with the exact declared profile and launch title. It tracks the manager process started by Loadstone; a manager window opening or closing is not evidence that the game started or exited. **Verify recipe files** separately repeats the complete static-file comparison and records the latest successful verification time. Later user edits may cause this comparison to fail; no file is repaired, overwritten or removed.

The full comparison is a point-in-time result. Registration rechecks metadata and the launch-critical files after review; launching does not rehash every mod file. Close other MO2/game windows yourself, including windows started outside Loadstone.

### Steam game startup

For a Steam edition, keep the owning Steam client running before **Launch native setup**. If New Vegas displays `Application load error 5:0000065434`, close the game and its MO2 instance, exit Steam normally, reopen Steam, then retry the same setup from Loadstone. A normal client restart resolved this error in our [isolated TTW menu test](native-steam-acceptance.md#direct-launch-after-a-normal-steam-restart). The [Viva New Vegas FAQ](https://vivanewvegas.moddinglinked.com/faq.html) also describes launching the owned game once through Steam as another recovery step. Launching the owned game that way is separate from launching the isolated modded setup.

If the error persists, retain the setup and record the exact error, game edition and Loadstone build before further diagnosis. A full reconstruction or a changed app ID is not established as a remedy by this test. Loadstone does not automatically restart Steam or change its registration. Reaching the menu and verifying a recording still leave new-game, save/reload and controller acceptance outstanding.

## Shortcuts and local state

Desktop and Steam buttons create or repair shortcuts to the candidate's manager and exact profile. Creation checks the same launch layout. Desktop links use the registered candidate ID as an ownership marker. Steam preserves unrelated entries and existing owned app IDs, backs up its shortcut file, and requires Steam to be completely closed. Choose the intended local account before saving.

These shortcuts start MO2 directly. They do not run Loadstone's checks again when clicked; use the library's launch button to recheck the current layout. Actual Steam-client/gameplay acceptance remains outstanding.

`native-library.json` in app data stores up to 100 registrations: local path and directory identity, recipe hash, title/version/profile, save guidance, output count and verification time. It contains no Nexus key or source archives. Writes preserve the previous registry if replacement fails, and refuse externally changed or unsupported state. Restart restores registrations without verifying or launching candidates automatically. Native verification prevents closing Loadstone until it finishes or cancellation completes.

Registered native entries now offer [reviewed removal and recovery](native-maintenance.md). Only unchanged, reviewed recipe files may be deleted after confirmation; saves, configuration, modified files and untracked content are retained. Interrupted removal and owned-shortcut cleanup can be retried. Removed entries retain their recovery record; migration to the current schema is described below.

[Native repair](native-repair.md) restores missing or changed recipe outputs in the registered folder, retains replaced files and preserves existing configuration by default. Interrupted repair blocks library launch until a fresh review and successful completion. Registrations now migrate to schema 3 when written, retaining removal state and adding a separate repair record. [Native version updates](native-updates.md) build a separate candidate while retaining the original setup and saves. Automatic save migration remains unfinished. [Interrupted creator builds can be reviewed and resumed](native-build-recovery.md) before registration. Wabbajack removal controls apply only to Wabbajack jobs and have their own preservation policy. Real install-to-play acceptance and pack publication remain separate gates.

# Resume an interrupted build

Canonical source: `docs/native-build-recovery.md`

Downloads offers **Review resume** for failed, cancelled and interrupted builds. Select the same `.loadstone` package and reselect its inputs through the [guided installer](native-guided-install.md), plus a trusted local archive tool when required. The creator path in Settings → Reconstruct a local candidate still accepts a private local-inputs JSON. Source paths and credentials are not saved in build history. The existing history record fixes the destination; the renderer cannot substitute another folder.

Keep MO2, supported games, script extenders and Wabbajack closed. Resume checks this before review, before acquisition and again before reconstruction. The candidate cannot overlap a registered native setup, another build, source inputs, app data or protected application/system folders. Completed library installations use separate maintenance controls; build resume is not an update or repair operation for an active playthrough.

## Review and confirmation

Review checks the recipe fingerprint and reconstruction metadata, scans the ordinary candidate tree and hashes existing outputs against their static or generated expectations. It reports matching files to reuse, missing files to build and conflicting files to preserve before rebuilding. Generated MO2 configuration is compared against the exact destination-specific bytes. Dismissing or cancelling the review changes no candidate files. Review progress is measured and cancellable; it is not persisted as an active build.

**Resume candidate** is explicit confirmation to reconstruct the same recipe. All required source inputs and archive structure are verified again before candidate writes. Existing reviewed file identities and timestamps, metadata fingerprints and the root identity must still match. Changed or replaced files after review stop recovery and require a fresh review. Existing matching outputs are left in place and included in final verification; only missing or conflicting outputs are written.

Conflicting files are moved, without replacement or deletion, into a unique folder below `<candidate>/.loadstone-build-recovery/`, retaining their relative paths. The previous reconstruction receipt is copied there too. Output creation remains exclusive. This preserves modified profile/configuration files as copies while restoring the recipe version in the candidate; review these copies before manually carrying settings into another version. Untracked files and saves remain in place. Recipes cannot target `.loadstone*` paths or save directories.

Only Loadstone opens destination paths; archive tools emit bytes to the existing bounded readers. ZIP, 7z and RAR reuse the same source and extraction validation as a new build. Verified cached downloads are reused. Interrupted partial downloads still restart from the beginning; this feature resumes candidate files, not byte ranges in downloads.

## Failures and restarts

Cancellation or failed writes retain the candidate and all recovery copies. Files already reconstructed remain available for the next review. A crash after retaining a conflict but before writing its replacement leaves the retained copy and a missing output; a later review rebuilds that output without deleting the copy. No automatic rollback, recovery-folder deletion or save migration occurs.

The same history entry records the resumed attempt. Restart converts active history into `interrupted` without continuing reconstruction. A failure before a candidate directory exists can retry that reviewed destination; a directory appearing after review is refused. A hard kill before both initial recipe and receipt metadata exist cannot establish the partial folder's provenance: preserve it and create a new candidate instead. Missing, corrupt or incompatible metadata is not guessed or repaired.

History remains schema 1, with no saved source map or recovery plan. External history changes or failed persistence stop new work and require restart. `materializing`, `failed`, `cancelled` and `verified` receipts can be reviewed for a failed/interrupted history entry; this handles a crash after final verification but before history was saved. Successful resume still says **Files verified · Launch untested** and does not register, launch or create shortcuts automatically.

Destination free-space checks count outputs still needing reconstruction plus recipe metadata and the normal reserve. Existing matching outputs and retained same-volume copies are not charged as a complete second installation. All final outputs are rehashed before success. These checks supplement Windows access controls; they are not a sandbox against an actively hostile process racing filesystem changes.

This workflow is available through the desktop builder. The local CLI still requires a new destination. Native library updates, clean-machine install-to-play, game/save compatibility and actual Steam-client acceptance remain separate work.

# Repair a setup

Canonical source: `docs/native-repair.md`

**My library → Repair native setup** imports the exact `.loadstone` recipe used by that registration and opens the guided source selections in Discover. Repair keeps the registered version, folder, profile and library ID. It does not update to a different recipe or version. Keep MO2, games and script extenders closed throughout review and repair.

Select owned games, prepared prerequisites and original archives again. Sources are not retained in the library registry. Downloads follow the same original-source, cache, hash and Nexus membership rules as installation. Select a trusted local archive reader when required. The current implementation revalidates all declared source inputs, including archives for outputs already present; it does not yet resolve only the sources needed for damaged files.

## Review and confirmation

Review hashes recipe outputs and shows matching, missing and changed files. Matching files are reused without rewriting them. Missing files are reconstructed. Changed game/mod files are moved to a unique `.loadstone-repair-recovery/<id>/` folder before replacements are written; an existing retained copy is never overwritten. Changed files, roots or metadata after review require another review.

By default, existing changed profiles and configuration are preserved. This includes `profiles/`, `overwrite/`, `downloads/`, and files ending in `.ini`, `.json`, `.toml`, `.yaml`, `.yml`, `.cfg`, `.conf`, `.fos`, `.ess`, `.nvse`, `.skse`, `.f4se` or `.bak`. Review displays the number of changed personal files retained and up to 20 paths. Missing recipe configuration is restored because no existing file is being replaced. Saves cannot be recipe outputs; untracked files and save directories are not written or removed.

The separate **Restore changed profiles and configuration to this recipe too** option also restores declared profile/configuration files, retaining their previous contents before replacement. It may reset recipe mod ordering or settings. Existing `downloads/` and `overwrite/` recipe files remain preserved even with that option. This choice does not migrate/import saves, run a converter, or delete untracked content. Changing the policy invalidates the reviewed plan.

**Repair installed setup** writes a durable `repairing` library record before acquisition or candidate changes. My library shows progress and cancellation. Completion verifies replacements against recipe hashes, retained personal files against hashes captured during review, and the current launch-critical executables and isolated-profile layout. Unsafe preserved MO2/profile settings prevent completion; review again with an explicit configuration restore or correct the local settings before retrying. Completion does not launch the manager or game.

## Recovery and state

Cancellation, failed writes or process interruption retain the existing setup and all recovery copies. Library launch and shortcut creation remain disabled while repair is incomplete. **Review repair again** reselects the same package and source inputs, reviews current files afresh and continues in the same installation. A failure after retaining an original but before writing its replacement leaves both the retained original and the missing/partial replacement available for that review. Removal remains available for a stopped repair under the existing save-preserving removal policy.

Existing Desktop/Steam shortcuts start MO2 directly and cannot enforce Loadstone's repair state. Keep games and managers closed until repair finishes. No automatic rollback, recovery-folder deletion, version update or save migration is provided by this operation.

The original reconstruction receipt remains unchanged and is retained in each attempt's recovery folder. It records the original reconstruction; the library's repair record describes later maintenance. Schema-1/2 registrations migrate to schema 3 on the next successful state mutation, without eager writes. Schema 3 adds repair recovery directory, start/completion time and preserved-file count. An interrupted `repairing` record becomes `repair-failed` on restart. Unreadable/newer state and external registry edits are refused. Failed final state persistence requires restart and a fresh repair review.

The last strict recipe verification timestamp is not advanced by repair when personal files are retained. **Verify recipe files** can still report intentional local differences after successful repair. A repaired setup has passed the repair's replacement/preservation and launch-layout checks; actual gameplay/save compatibility still requires separate acceptance.

## Verification scope

Synthetic service tests cover missing/changed files, retained originals, personal files and save canaries, explicit configuration restore, redirected/stale paths, protected registry writes, active managers, cancelled work, failed replacement after retention, failed final persistence, restart/retry, schema migration and original RAR acquisition. Actual Electron exercises library-to-Discover repair review, preservation, reconstruction and restart persistence. No fixture executable is run; real game, Desktop and Steam installations remain outside these tests.

This workflow offers a recoverable fresh-install update, not verified game/save compatibility. # Remove & recover

Canonical source: `docs/native-maintenance.md`

**My library → Remove native setup** reviews a registered candidate before showing a native confirmation dialog. Keep supported games, script extenders, MO2 and Wabbajack closed. The process check must succeed before review and again before removal. No game or manager is started by this workflow.

The review scans the ordinary candidate tree and compares potentially removable files with recipe sizes and SHA-256 hashes. It reports the maximum reviewed file count/bytes, retained file count and exact recovery path. Cancelling this review or its confirmation changes no candidate files.

## What is kept

Only static recipe outputs whose current bytes match the recipe may be selected for deletion. Everything else is retained, including untracked files and modified recipe outputs. The following are always retained even when they match the recipe:

- All content under `profiles`, `overwrite` and `downloads`, and any directory named `saves`.
- Configuration files ending in `.ini`, `.json`, `.toml`, `.yaml`, `.yml`, `.cfg` or `.conf`.
- Save/co-save/backup files ending in `.fos`, `.ess`, `.nvse`, `.skse`, `.f4se` or `.bak`.
- `.loadstone*` metadata. The generated MO2 configuration is retained.

After confirmation, Loadstone durably records `removing`, rechecks the root identity and protected locations, then moves the entire candidate into a sibling folder named `<candidate>.loadstone-recovery-<registration-id>`. It never replaces an existing recovery folder. It rehashes each selected file and checks that its identity and timestamps still match the review before unlinking it. Edited or replaced files are kept, including same-byte replacements with a different identity. Newly created files are never added to an existing removal plan. Only empty ancestor directories of deleted files are cleaned up; the recovery root remains.

The recovery folder is retained data, not a playable installation. Its manager configuration still describes the original destination. Do not launch it directly or copy saves into another version without checking that version's save guidance. Removing a setup does not delete a source game, archive cache outside the candidate, global save folder or another registered setup.

## Interruptions and shortcuts

**Stop removal** stops further work after the current asynchronous operation observes cancellation. Files already deleted are not restored. Remaining content stays in the original or recovery folder, and the entry offers **Resume native removal**. Resuming requires a fresh review and confirmation; missing files are skipped and remaining files are checked again. A restart converts durable `removing` state into an interrupted state without automatically continuing deletion.

Redirected entries, replaced roots, changed reconstruction metadata, protected-folder overlap, a conflicting recovery folder or an unavailable state file stop the operation. Preserve the directories and registry when resolving such a conflict. No broad recursive deletion is used. A failed registry write before the initial move leaves the candidate in place; a later failure leaves a resumable durable record.

After file removal, Loadstone removes only its identified Desktop and Steam shortcuts. Steam must be completely closed to edit its shortcut file. Cleanup failures remain visible and **Clean up native shortcuts** retries them without rerunning file removal. Existing Steam backups and unrelated entries remain intact.

Removal recovery was introduced in schema 2; native library state is now schema 3 with repair records. Schema-1/2 registrations migrate in memory without an eager disk write and are saved as schema 3 on the next successful mutation. Older builds reject the newer state; preserve app data before downgrading. Removed entries remain as recovery records; there is no automatic recovery-folder deletion or history pruning.

[Native library repair](native-repair.md) now has its own reviewed reconstruction and retained-copy workflow. Stopped repairs may also use this removal policy. [Native version updates](native-updates.md) create a separate installation with fresh recipe settings. Automatic save migration remains separate work. [Interrupted candidate builds have their own resume review](native-build-recovery.md). Synthetic and actual-Electron tests prove the controlled removal/recovery behavior, not real gameplay, save compatibility or Steam-client acceptance.

# Wabbajack installation

Canonical source: `docs/installation.md`

Disable dummy data in Settings, prepare the pinned engine, connect a Nexus account if the list requires it, then import a creator manifest with its original Wabbajack archive. Check compatibility in Discover. Installation becomes available only after all checks pass; starting repeats the checks. Wabbajack must resolve the same game folder selected in Loadstone. Lists requiring unsupported providers or manual Nexus downloads are blocked.

Only one live installation runs at a time. Downloads displays actual engine output and job phases, without estimating a percentage from elapsed time. Library entries appear only after the engine exits successfully, structural profile verification passes, and the declared output files are checked. Structural checks cover the manager executable, configuration, declared profile and launch target. Output checks revalidate the owned list archive SHA-256, require every final declared file to be a regular file within the profile, reject redirected paths, and compare sizes for InlineFile, FromArchive and PatchedFromArchive outputs. INI files, modlist.txt, remapped and other generated outputs receive presence/path checks because their content may legitimately change. Temporary BSA inputs are excluded when the list declares CreateBSA outputs; the final BSA files are still required.

The pinned [upstream installer](https://github.com/wabbajack-tools/wabbajack/blob/4.2.3.0/Wabbajack.Installer/StandardInstaller.cs) rewrites configuration and removes [temporary BSA inputs](https://github.com/wabbajack-tools/wabbajack/blob/4.2.3.0/Wabbajack.Installer/Consts.cs). Output verification records its checked counts and completion time; Library shows these as installation-time evidence, not a continuous integrity guarantee. A missing file or size mismatch leaves the job failed and retryable. Cancellation during verification also remains retryable. The checks do not establish installed-file checksum integrity or gameplay correctness, and existing installations are not retroactively labeled verified.

## Launching

Library offers **Launch setup** and **Check profile**. Launch repeats structural checks, requires the original `portable.txt` marker, and rejects a redirected MO2 profile directory. It invokes the installed manager with `-p <profile> run -e <configured executable title>` as separate process arguments, using the manager directory as its working directory. No shell interprets titles or paths, and inherited Nexus credential variables are removed. This adapter targets MO2's standard portable layout and the command interface present in [MO2 2.5.2](https://github.com/ModOrganizer2/modorganizer/blob/v2.5.2/src/commandline.cpp). The [portable marker behavior](https://github.com/ModOrganizer2/modorganizer/blob/v2.5.2/src/instancemanager.cpp) keeps instance selection local.

Status tracks the spawned manager process, not gameplay or playtime. MO2 may hand the request to an existing window; check that window for game startup or errors. Closing Loadstone leaves the manager/game running. Manager tracking is session-local and does not survive a Loadstone restart.

## Steam library entries

Library offers **Add or repair Steam entry**, with explicit local-account selection. Steam must be fully closed; Loadstone checks for Steam processes twice and never closes Steam itself. With the Steam shortcut preference enabled, installation attempts automatic creation only when one local account is available. If Steam is running, no account exists, or account selection is ambiguous, installation remains successful and the library reports the follow-up needed.

Entries target the same portable MO2 command as desktop shortcuts. The updater understands the binary KeyValues format used by `userdata/<account>/config/shortcuts.vdf`. It preserves unrelated entries as their original bytes and preserves the app ID and additional fields when repairing a matching Loadstone entry. A per-installation tag identifies ownership. Name/app-ID conflicts, malformed or unsupported data, redirected files and concurrent file changes stop the edit. Existing files receive a uniquely named `.loadstone-<id>.bak` backup before replacement. To restore one, exit Steam and copy the desired backup over `shortcuts.vdf`; this restores the entire previous shortcut library.

This is a local-file integration, not a public Steamworks shortcut API. Format references: [ValvePython's binary KeyValues implementation](https://github.com/ValvePython/vdf) and [SteamTinkerLaunch's shortcut integration](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Add-Non-Steam-Game). Tests use isolated Steam directories. Read-only inspection of the development machine's existing three-entry shortcut file confirmed an exact binary round trip. Creating an entry and launching it from the actual Steam client still needs release acceptance testing; neither the tests nor this inspection changed that real shortcut file.

## Desktop shortcuts

When the desktop shortcut preference is enabled in Settings, successful installation creates a Windows `.lnk` on the user's Desktop. Library also offers creation and repair. Creation repeats launch checks, quotes each Windows argument, writes a temporary link through [Electron's native shortcut API](https://www.electronjs.org/docs/latest/api/shell/), reads it back for verification, and then publishes it. The target is the installed MO2 executable, with the same profile, configured launch title and working directory as library launch. The shortcut works without Loadstone open; it therefore does not repeat Loadstone's checks when double-clicked.

Each filename and description includes the installation ID. Repair recreates a missing link or replaces the matching owned link. It refuses to overwrite a link with a different ownership description. Shortcut errors appear separately and leave a successful installation installed. The displayed path records the last successful creation; it is not a continuously checked existence indicator. Tests use a temporary Desktop folder and real Windows shortcut read/write calls, leaving the user's Desktop untouched.

## Owned files and recovery

The selected destination must initially be empty. Loadstone records an ownership marker and creates `profile/` for Wabbajack output, `downloads/` for reusable archives, `work/` for the engine working directory, and a hashed `list.wabbajack` snapshot. Retry requires matching ownership and preserves downloads and partial output. It also repeats preflight against the imported manifest and source archive; keep those available. Changed source manifests may prevent a retry of the original snapshot.

Closing the window or quitting while installation, removal or engine preparation is active keeps Loadstone open and offers minimization. Finish the operation, or stop installation in Downloads / cancel engine preparation in Settings and wait for its stopped status before closing. This avoids exiting before final state and log cleanup are saved; forced termination, Windows shutdown and crashes still use interruption recovery.

Cancel stops the tracked engine process tree. Completion is recorded only after the child exits. An unexpected app interruption leaves a durable job that becomes interrupted on reopening. Restart Windows before retrying that job: the saved Windows boot identifier prevents reuse while the previous engine might still be running. Loadstone does not automatically restart interrupted work.

## Credentials and diagnostics

The main process passes the private-test Nexus key only to the engine environment. Renderer job history contains no key. Captured output redacts the exact key, URL queries and named token fields, retaining at most 150 lines of 1,000 characters each. After the child exits, matching Wabbajack CLI logs in the owned working directory and Loadstone-managed runtime directory are sanitized; oversized logs are replaced with a short notice. Native engine logs may remain unsanitized while installation is running or after a crash. Do not publish raw engine logs without reviewing them. Third-party diagnostics outside those two managed locations are not covered by this sanitizer.

## Removing a setup

**Remove setup** checks ownership and scans the installed profile before presenting a native confirmation dialog with the exact destination, recovery folder, file count and estimated file bytes to remove. Supported game, script extender, MO2 and Wabbajack processes must be closed. Loadstone will not stop them automatically. Junctions and symbolic links anywhere inside the profile block removal, as do overlaps with game, system or application folders.

On confirmation, Loadstone records durable removal state and moves the owned destination to a sibling folder named `<destination>.loadstone-recovery-<installation-id>`. It deletes ordinary installed files inside `profile/` while retaining all of `profile/profiles/`, `profile/overwrite/`, `ModOrganizer.ini`, and any directory named `saves`. Downloads, the list archive, engine logs and other files outside `profile/` remain in the recovery folder. Global saves outside the setup are untouched. Custom mods and other files inside `profile/` outside the retained locations are deleted; copy anything else you want to keep before confirming.

No recursive deletion follows reparse points. Each file is checked again before deletion. If a file is locked or the app closes, the job becomes resumable removal work; **Resume removal** repeats the checks and continues. A completed removal leaves the library and stays in Downloads history with its recovery location. The original destination can be used for a fresh installation. The retained data is not a full restore of deleted mods; transferring saves to another list requires that creator's save-compatibility guidance.

After removal, Loadstone deletes its matching desktop link and tagged Steam entries across available local accounts. Unrelated shortcuts are retained. Steam must be closed for any Steam file edit; each edit gets a backup and preserves remaining entry fields and app IDs, renumbering entry indices where necessary. Cleanup failures leave the setup removed and show **Clean up shortcuts** in Downloads for retry, including after restart. Renamed desktop links and unavailable Steam accounts may require manual cleanup. Version updates use separate fresh installations with creator-declared save guidance; see [updating manifests](manifests.md#updating-an-imported-setup). The previous setup remains available until explicitly removed. Deleting the recovery folder would delete the retained saves and downloads, so Loadstone does not purge it automatically.

## Verification status

Tests exercise real child processes with synthetic files: success, failure, cancellation, retry, ownership rejection, restart recovery, credential redaction, launch arguments, duplicate launch prevention and manager exit handling. Electron tests cover library profile checks and demo-mode launch rejection. The pinned official engine has separately passed integrity, version, help and game discovery checks. A full real list download, install and play session has not yet passed acceptance testing. These source features are newer than the v0.1.0 portable preview.

# Creator workflow

Canonical source: `handbook/pages/creator-workflow.md`

Start with a specific installed version and its chosen profile. An upstream list is a useful lead, but it does not necessarily describe local changes, generated output, disabled mods or the files that are actually in use.

## 1. Capture installed truth

Use the [inventory tooling](../../docs/installed-inventory.md) to record hashes, mod ordering and enabled states, profile configuration, instance/game files and overwrite content. Preserve existing saves and live installations. Keep the inventory outside source control: it contains private paths and installed-content names.

## 2. Find and prove sources

Build a private source ledger from the accepted inventory and selected download folders. Add explicit creator hints when automatic archive leads are incomplete. Compare original ZIP/7z/RAR members by exact size and SHA-256. An adjacent metadata ID is a lead, not proof of the file's contents or its rights.

For installed BSA containers, use [nested BSA mapping](../../docs/bsa-inspection.md#nested-source-mapping) to verify the original member and its internal files. Keep unresolved generated/edited files visible. A similar filename or rendered image is not an exact replacement.

## 3. Review rights and required inputs

For every distributed source or asset, record authorship, attribution, permitted delivery and the required user-owned inputs. Original downloads, local owned-game reconstruction and hosted payloads are distinct cases. A local file that happens to install successfully is not automatically redistributable. Loadstone's GPL license does not grant rights to third-party mods or game files.

## 4. Write a typed recipe

Use the [format reference](../../docs/loadstone-format.md) for exact field names and limits. Declare outputs with hashes and required timestamps. Prefer original archive sources when supported; declare prepared prerequisites honestly where automatic conversion is not implemented. Configure portable MO2 with the [destination-bound configuration action](../../docs/native-mo2-configuration.md). Do not import account/browser state or arbitrary shell scripts.

## 5. Compile and inspect

Compile the recipe into a package and inspect it before reconstruction. Review source hosts, requirements, output paths, storage, profile and save guidance. Package validation must succeed independently of any installed baseline used to create it. The native [reconstruction guide](../../docs/native-reconstruction.md) documents CLI and desktop entry points.

## 6. Reconstruct and compare

Build into a new isolated candidate. Verify every required output and declared timestamp, then compare against the intended baseline. Exercise cancellation, reviewed resume and relevant maintenance behavior with disposable candidates. Do not substitute a successful inventory scan for actual reconstruction.

## 7. Accept the playable setup

Review library admission, launch, shortcuts, a disposable new game, save/reload and the intended input devices. Repeat on a clean Windows environment with the required owned games and sources. Record exact app, recipe, game, manager and tool versions. A menu launch is only one step.

## 8. Prepare publication

Complete credits, source permissions, support instructions, truthful screenshots and the release checklist. Featured status indicates Loadstone maintenance, not endorsement by upstream authors or publishers. Publication remains a separate action after the [acceptance gates](../../docs/1.0-plan.md) are met.

# Inventory & source mapping

Canonical source: `docs/installed-inventory.md`

This work uses the selected profiles of the user's installed setups as the source of truth. Original modlist archives are source hints, not authoritative descriptions of the current installation. No live profile, mod, game, save or shortcut is modified by inventory.

## Read-only inventory

```powershell
node scripts/inspect-mo2.mjs <portable-instance> <new-local-report.json>
node scripts/inspect-mo2.mjs <portable-instance> <new-local-report.json> --hash-files
node scripts/inspect-mo2.mjs <portable-instance> <new-local-report.json> --hash-files --installation-files
```

Keep reports under ignored `test-results/` or another private local directory. They contain personal paths and local filenames and must not be committed or published. The CLI refuses to replace a report. It reads the selected MO2 profile, resolves configured mod/profile locations, preserves the profile's recorded priority, inventories enabled mod directories and overwrite, and hashes profile files plus the installed loose plugin winning each conflict. Known source fields from `meta.ini` are hints only; other fields are excluded.

Default file inventories record size and modification time. `--hash-files` additionally hashes every included enabled-mod and overwrite file. Add `--installation-files` to include selected-profile disabled mods, instance files and tools, the configured game directory, and all files in the selected profile, including configuration outside the original six-file snapshot. The additive `installation` record carries `instanceFiles`, `gameFiles` and `profileFiles`; mod records keep their original enabled/disabled state and priority. Unlisted mod directories and other profiles are outside this selected-profile baseline.

Configured mod/profile/game/overwrite directories are captured separately without duplicating their contents under the instance tree. The configured download cache is excluded. All scans skip known save/cosave paths, credential/browser stores, logs, caches and backup directories by path, before opening them; each excluded file or subtree is recorded with its scope and reason in `exclusions`. This is an explicit inventory boundary, not a claim that excluded state is reproducible. General configuration can contain private fields: its content is hashed, while only the existing allowlisted source hints are exported. Reports remain private. No file is executed, edited or uploaded.

Neither mode is an atomic filesystem snapshot. File hashing rejects changes while reading. At the end, every scanned tree is enumerated again and checked for added/removed files, file identity/size/timestamp changes and replaced directories; selected profile/configuration hashes are also rechecked. Stop active modding or gameplay before producing release evidence. Symlinks/junctions outside excluded state, ambiguous INI fields, duplicate mod entries and traversal names are rejected. Missing enabled mods/plugins are reported explicitly, not called a successful installation. Ctrl+C cancels scanning; no final report is written. Across scanned trees, inventories are bounded to one million included files, 100,000 excluded paths and 100,000 directories per tree.

The report is **not installable and not publication-approved**. Even with complete hashes for the included files, it does not establish upstream game equivalence, archive contents/conflict resolution, runtime compatibility, source-download reproducibility or redistribution rights. Saves are not read from the profile. No network request or program launch is required to inspect an instance.

MO2 instance plugin inventories also exclude CPython `__pycache__` files when their adjacent ordinary `.py` source is present. Each receives the explicit `regenerable-python-bytecode` reason; the source remains inventoried. Standalone bytecode, caches without a source, unknown cache naming and mod/game content remain included. This avoids pinning machine-dependent cache bytes that MO2 regenerates after relocation. Existing inventories, recipes and verification fingerprints are unchanged; use a new reviewed recipe/version to apply this boundary.

Winning loose-plugin records also retain `mtimeMs` (UTC milliseconds, rounded to an integer) alongside their SHA-256, size and winning layer. This is collected from the same stable hash pass. It lets a creator explicitly preserve timestamp-based load order in a new recipe without assigning that metadata to every mod file or silently changing existing reports. Hash-mode file inventories otherwise retain their existing size/hash shape.

## Private source ledger

```powershell
node scripts/source-ledger.mjs hashed-inventory.json new-private-ledger.json downloads-folder [another-downloads-folder]
node scripts/source-ledger.mjs hashed-inventory.json new-private-ledger.json downloads-folder --hints private-hints.json
```

This command preserves the hashed installed-file records and finds candidate ZIP/7z/RAR archives using the recorded installation filename or a matching game/mod ID. It fingerprints candidate archives and reads only `gameName`, `modID` and `fileID` from their adjacent `[General]` metadata. It does not read credential header files, copy arbitrary metadata fields, extract archives or contact Nexus. Conflicting metadata and multiple versions remain explicit candidates; none is selected automatically.

Expanded inventories retain their instance/game/profile hashes and explicit exclusions in the private ledger, with an allowlist of record fields. Inventoried disabled mods can receive archive candidates and exact member matches without being enabled. These added root/profile records remain unresolved until separately mapped or transformed; retaining hashes does not infer their sources or permission to distribute them.

The resulting ledger references the input inventory's SHA-256 and records unresolved reconstruction and unreviewed permissions. Matching a filename or Nexus mod ID does not prove an archive member equals an installed file. Exact member comparison, local edits, root/profile reconstruction and generated output remain separate work. Keep these ledgers private alongside inventories; the CLI refuses to replace them or write inside source/download directories.

When installed metadata cannot identify an archive already in the selected download folders, a creator can nominate it with a private UTF-8 JSON hints file:

```json
{
  "schemaVersion": 1,
  "kind": "loadstone-source-hints",
  "mods": [
    {
      "name": "Example installed mod",
      "archives": ["C:/CreatorCache/original.zip"]
    }
  ]
}
```

Each name must exactly match one inventoried mod with files, including disabled mods. Archive paths must be absolute and identify top-level ZIP/7z/RAR files in a download folder explicitly selected on the command line. Unknown fields, duplicate mod names or per-mod archive paths, redirected files and paths outside those folders are rejected. Limits are 5 MB per hints file, 10,000 mods, 100 archives per mod and 100,000 total references. Hints cannot add remote URLs, credentials or claimed provider IDs.

Hinted archives are fingerprinted and marked `creatorHint: true`; existing automatic match evidence is retained without duplicating a candidate. Conflicting known game/mod metadata remains a conflict and is skipped during member mapping. A hint never proves installed bytes, rights or reconstruction. The ledger retains the hints file's path and exact SHA-256; ledger creation rejects a changed hints file, and mapping refuses a hints file that has changed since the ledger was written. Keep that file private and stable alongside the reports. Ctrl+C cancels ledger creation without writing a final report.

```powershell
node scripts/map-zip-sources.mjs private-ledger.json new-private-mapping.json
```

The member mapper verifies each candidate ZIP against its locked archive hash, then streams member hashes and compares them with installed size/SHA-256 pairs. It records exact member paths, retains matching archive candidates and leaves locally changed files unresolved. It does not extract files or execute content. MO2 `meta.ini` is excluded because it needs privacy-aware regeneration. Each ZIP is accepted as a whole: unsafe paths, duplicate/colliding names, links, changed input or limit violations discard its potential matches. A cancellation aborts the pass.

Upstream ZIPs may use Windows backslashes in their internal names. These separators are normalized to `/` before path validation, collision checks and member selection; the original archive is never rewritten. Slash/backslash aliases, case collisions, traversal, absolute paths and file/directory overlaps still reject the entire archive. Mapped member paths use canonical forward slashes and can be passed directly to native reconstruction. `.loadstone` package entries and recipe paths remain strict and do not accept backslashes.

Limits per archive: 50 GB compressed input, 500,000 entries, 100 GB declared uncompressed content, 1 GB per hashed member and 20 GB of hashed member data. The report accepts at most 500,000 match references. Exact byte matches still require source/rights review, profile and root reconstruction, and actual installation acceptance.

When multiple members of one archive have identical size and SHA-256, the mapper keeps the lexicographically first normalized member path as a deterministic representative and records `equivalentMembers`, the count of verified members with those exact bytes. The mapping declares `memberSelection: "lexicographic-representative-per-content"`. This compact representation replaces the earlier 128-equivalent-member rejection and prevents the installed-file count from multiplying by the number of identical copies. Every selected member is still hashed; complete archive validation and stream checks must succeed before any matches are accepted. Different archives remain distinct candidates. A representative proves a byte-equivalent source, not which archive member the original installation used. Recipes still require review of the source and exact selected member.

For optional 7z/RAR comparison, pass an absolute path to a trusted local x64 `7z.exe` (26.04 or newer, with its matching `7z.dll`):

```powershell
node scripts/map-zip-sources.mjs private-ledger.json new-private-mapping.json C:\Tools\7-Zip\7z.exe
```

The command retains its original name for existing workflows; this optional argument enables the additional formats. Archive signatures select the parser, so a ZIP cached under a `.7z` filename can be inspected without renaming or altering it. A signature only selects the parser; full archive hashes and structural validation still apply. Embedded/self-extracting formats remain unsupported. The tool path comes from the operator, never from a recipe. It runs without a shell or visible window, inventories the archive, rejects encrypted/linked/multipart/embedded or ambiguous entries, and reads each selected member into a bounded hashing stream. Nothing is extracted to disk. Literal selectors disable wildcards and list-file expansion. Archive and executable/library identities are checked between reads. Tool diagnostics stay out of reports.

For 7-Zip 26.04 and a Node runtime with `zlib.crc32`, bounded 7z archives with member CRCs use one streamed pass. The reader checks every file boundary against its listed CRC, computes SHA-256 for wanted sizes and accepts matches only after the complete stream, exit status and source identity pass. It handles up to 100,000 selected members and 20 GB of total streamed content without writing extracted files. The implementation was checked against upstream [listing order](https://github.com/ip7z/7zip/blob/26.04/CPP/7zip/UI/Console/List.cpp), [extraction indices](https://github.com/ip7z/7zip/blob/26.04/CPP/7zip/UI/Common/Extract.cpp) and [7z solid-block extraction](https://github.com/ip7z/7zip/blob/26.04/CPP/7zip/Archive/7z/7zExtract.cpp); a boundary mismatch discards all matches.

Other tool versions, RAR and archives without suitable checksums use one process per selected member, which can be slow for solid archives and is limited to 10,000 selected members. Each archive has a five-minute budget; a timeout or limit records an unresolved issue. The single-pass reader accepts members over 1 GB within its unchanged 20 GB total stream bound; individual-member and ZIP comparison retain a 1 GB member bound. Hashing a BSA as one archive member does not map files inside that BSA. The same adapter also supports [native reconstruction](native-reconstruction.md), with separate extraction limits and operator-selected tool review. No 7-Zip binary is bundled with Loadstone.

For tests, `scripts/prepare-sevenzip.ps1 -Destination <new-private-directory>` downloads the fixed official 26.04 x64 release, checks its published SHA-256, and unpacks only the command-line tool and notices with an existing 7-Zip. It does not install globally. Set `LOADSTONE_TEST_7ZIP` to the returned executable when running tests. Windows CI performs this setup and runs the real tool fixture; without the variable that optional integration test is skipped.

7-Zip is a separate upstream tool with LGPL, BSD and unRAR terms; a future bundled distribution needs its own notices/source compliance review. See the [official release](https://github.com/ip7z/7zip/releases/tag/26.04) and [license](https://www.7-zip.org/license.txt).

For a separate read-only inventory of files inside a local Fallout 3/New Vegas BSA, see [BSA 104 inspection](bsa-inspection.md). To connect selected installed BSAs to original archive candidates and compare their contents with the ledger, use [nested BSA source mapping](bsa-inspection.md#nested-source-mapping). Reviewed source chains can then be declared explicitly for [native BSA reconstruction](native-reconstruction.md#nested-bsa-104-files).

## Native `.loadstone` format

The user chose a documented format and open implementation on 2026-10-13. This is Loadstone's native format, not an opaque replacement for upstream archives. The implementation and specification will be developed together from the real inventories. The maintainer separately selected GPL-3.0-or-later for the original implementation on October 13, 2026; third-party content retains its own terms.

The first [native format specification and package compiler](loadstone-format.md) are now available as experimental creator tooling. Inventory reports remain private evidence; they cannot bypass the source and rights work required for a valid recipe.

The target is a versioned, bounded container with a canonical recipe, source lock and content hashes. It must describe:

- Game/storefront/DLC requirements and exact accepted source hashes; TTW requires both owned games while running through the New Vegas engine.
- Mod priority, enabled and disabled state, plugin order, archive behavior, loose-file overrides, root files and generated output.
- Source URLs/provider file IDs and original archive hashes; an installed version string alone cannot identify a reproducible download.
- Differences between original archives and installed files, including locally edited INIs, generated LOD, compatibility patches, custom assets and menu-music transformations.
- Typed, bounded local reconstruction operations. No arbitrary shell recipes or remote scripts.
- A rights record for each payload: original source download, local owned-game input, redistributable content with evidence, or unresolved. Unresolved records block publication of the affected payload.
- Save compatibility, provenance, attribution and exact tested application/list/game versions.

A public list recipe must exclude personal machine paths, accounts, saves and raw logs. Source hashes and dependency references can describe a setup without uploading its game/mod payload. Any bundled files need separately established distribution rights. Local custom menu music built from owned game themes must be reconstructed locally or replaced with permitted material, not assumed redistributable.

## Compatibility and hosting boundaries

# The .loadstone format

Canonical source: `docs/loadstone-format.md`

Status: experimental creator tooling. This is a documented format with an original implementation licensed under GPL-3.0-or-later. The source repository is public; recipes and payloads require their own distribution rights and acceptance. **Settings → Native package preview** inspects a user-selected package through the Electron bridge and shows a bounded summary. **Reconstruct a local candidate** can build local copy and ZIP/7z/RAR-extract recipes with durable history. Guided native installation and explicit library admission are implemented alongside the Wabbajack path; actual game/list acceptance remains required before advertising a supported playable setup.

## Purpose and trust boundary

A package describes exact inputs and expected outputs for a portable, isolated MO2 setup. It references original downloads and locally owned game files. It can carry small payloads with declared distribution permissions. It has no shell actions, scripts, hooks, remote executable recipes or implicit path discovery. An archive source names a specific archive; an extract action names a specific member, without interpreting that member's extension as an instruction.

The installed inventory is separate private evidence. It is not a recipe: missing archive provenance, local changes, generated content and permissions must be resolved before compilation. A Nexus mod ID alone is insufficient. Do not replace a current custom installation with its upstream list while calling it equivalent.

SHA-256 verifies byte identity, not safety, authorship or rights. Version 1 packages are unsigned. Permission fields are creator declarations with review references; the validator cannot establish legal permission or approve publication. Gameplay, save compatibility and publisher trust require separate acceptance. Inspection always returns `publicationApproved: false`.

## Container

Use the `.loadstone` extension for a ZIP with these entries:

1. `recipe.json`, first in central-directory order, containing canonical UTF-8 JSON.
2. `payload/<sha256>` for each declared payload source, exactly once. No other entries, directory records, symlinks, devices, encrypted files or file comments are allowed. ZIP methods 0 (stored) and 8 (deflate) are accepted.

Canonical JSON recursively sorts object keys using JavaScript's default string ordering, preserves array order, uses `JSON.stringify` compact serialization and appends exactly one LF. No BOM. The parser validates the object and requires byte equality with that representation, rejecting duplicate keys and ambiguous alternate representations. Numbers are bounded safe integers wherever used. Recipe identity is SHA-256 of these canonical bytes; ZIP compression and timestamps do not define recipe identity.

The reference compiler orders payloads by their lowercase hex hashes, uses fixed timestamps/modes and stored entries. Given identical inputs on the same toolchain it creates identical package bytes. Inspection streams payload hashing and never extracts or launches content.

Limits: 64,000,000 recipe bytes; 100,000 sources; 500,000 outputs; 256,000,000 total uncompressed bundled payload bytes; 512,000,000 package bytes; at most source-count-limit plus one entries. Byte sizes are nonnegative safe integers; download/output totals are capped at 10 TB. These are parser limits, not recommended list sizes or machine resource promises.

## Recipe fields

All objects reject unknown fields. All listed fields are required unless marked optional or a source/action variant omits them. `electron/native-format.cjs` is the executable validator; fixtures in `tests/native-package.test.mjs` show a complete synthetic example. This experimental version is not yet a stable interchange contract; older previews reject newer optional fields safely.

| Field | Meaning |
| --- | --- |
| `format`, `formatVersion` | Literal `loadstone` and integer `1`; unknown versions fail closed |
| `id` | Lowercase letters, digits and hyphens; 1–64 characters, starting with a letter or digit |
| `name`, `version`, `author`, `description` | Nonempty text up to 500 characters, without control characters |
| `website` | HTTPS reference without userinfo, query or fragment |
| `game` | `{id, variant}`; targets `fnv`, `skyrimse`, `fallout4`; variant `base`, or `ttw` for FNV |
| `requirements` | Exact owned-game inputs, below |
| `prerequisites` | Optional local material the user prepares separately, below; omitted when none |
| `launch` | `{profile, executable, gameRoot}`; MO2 profile directory name, MO2 executable title, isolated relative game directory |
| `sources` | Inputs keyed by unique `id`, below |
| `outputs` | Expected final files and typed reconstruction actions, below |
| `saveCompatibility` | `{status, notes}`; status `unknown`, `new-save-required` or `compatible`; guidance up to 2,000 characters |

FNV is the full support target. Skyrim SE/FO4 remain in development. Fallout 3 can appear only as an owned input to TTW; it cannot be the target. Starfield is not accepted. Schema acceptance does not certify a game or list.

### Owned games

Each requirement is `{id, store, files}`. `store` is `steam` or `gog`. `files` contains 1–10,000 `{path, bytes, sha256}` records and must include that game's executable. The requirement set is exactly the target game for a base recipe, or FNV plus Fallout 3 for TTW. A recipe represents one exact accepted storefront/file set; a different version requires a different recipe. The specification does not claim ownership can be established from a file hash alone.

These references instruct the materializer to read a user's local input. They grant no permission to bundle or mirror game content. TTW conversion, patching and version alternatives need additional typed operations and acceptance before native TTW installation can be claimed.

### Local prerequisites

An optional `prerequisites` array declares 1–20 `{id, name, version, instructions, credit, files}` records. IDs follow the source-ID syntax and are unique within the array. Names/versions are nonempty text up to 500 characters. `instructions` is a public HTTPS reference without credentials/query/fragment, never fetched or executed automatically. `credit` uses the source attribution shape. Each `files` array locks exact `{path, bytes, sha256}` records, with the same safe-path rules as owned inputs. Across prerequisites the limits are 100,000 files and 10 TB.

The user selects an existing folder for each prerequisite. Every locked file is checked before output creation, and source folders cannot overlap the destination. A `prerequisite-file` source copies a declared local file with an identical hash and byte length. Every prerequisite must supply at least one used source. This can represent a separately prepared dependency without bundling or mirroring its bytes. It is not proof of ownership, distribution permission or automated TTW conversion; the TTW variant still requires both owned games independently. Actual TTW integration remains unaccepted.

### Sources

Every source has `id`, `type`, `bytes` and lowercase 64-character `sha256`.

| Type | Additional fields |
| --- | --- |
| `game-file` | `game`, `path`; must match the path/hash/size of a locked requirement file |
| `prerequisite-file` | `prerequisite`, `path`; must match a file in that declared local prerequisite |
| `nexus-archive` | `game`, positive integer `modId`, positive integer `fileId`, `credit` |
| `https-archive` | `url`, `credit` |
| `payload` | `credit`, `permission`; exactly one corresponding container entry |

Nexus `game` is `falloutnv`, `fallout3`, `skyrimspecialedition` or `fallout4`. Credentials and download tokens are resolved at runtime, never stored in a recipe. A `credit` is `{name, url}`. A payload's `permission` is `{license, evidence}`, with a nonempty license description up to 200 characters and an HTTPS evidence reference. URL fields reject credentials, query parameters and fragments to exclude typical signed links and tokens; human privacy review remains necessary.

Every source must be used. Bundled hashes cannot be declared twice. Sources do not contain private local paths. The desktop's [archive acquisition layer](native-downloads.md) enforces network destination, redirect and account policy separately; accepting an HTTPS string is not permission to fetch arbitrary endpoints.

### Outputs and actions

Copy/extract outputs are `{path, bytes, sha256, action}`, optionally with `mtimeMs`. A generated MO2 configuration instead uses `{path, action}` with destination-specific fingerprinting as described below. File paths use `/`, are relative NFC strings up to 240 characters, and reject Windows device names, drive/UNC paths, alternate data streams, traversal, empty segments, trailing dots/spaces and reserved characters. Windows case-insensitive duplicates and file/directory overlap are rejected. Paths containing a `saves` component or a component starting `.loadstone` are reserved.

`mtimeMs` declares the output's last-modified time as integer UTC milliseconds since the Unix epoch, from `0` through `4102444800000` (2100-01-01). Use it when metadata affects behavior, such as timestamp-ordered Bethesda plugins. It applies only to copy/extract outputs, never their inputs or generated MO2 configuration. The installer sets it after reconstructing and hashing a fresh file, then verifies the stored timestamp rounded to the nearest millisecond. A filesystem that cannot represent it fails verification. Archive-member timestamps are not implicitly imported, and creation/access times are not recipe identity.

Full recipe verification and build recovery require both the declared bytes/hash and timestamp. A timestamp-only change becomes a recovery/repair conflict: preserve the old file before replacing it, and retain it during removal. Repair's existing default of preserving personal configuration still applies; explicitly restoring configuration is needed to recover its recipe metadata. Normal launch retains its existing executable/profile safety checks and does not perform full recipe verification. Omission preserves legacy behavior and canonical recipe identity. Adding the field creates a new recipe fingerprint; earlier readers reject the unsupported field rather than silently ignoring it.

- `{type: "copy", source: "source-id"}` copies a `game-file`, `prerequisite-file` or `payload`. Expected output bytes/hash must equal the input.
- `{type: "extract", source: "archive-id", member: "Data/Example.esp"}` selects one safe member of a locked Nexus/HTTPS archive. The output hash is the hash of the extracted member. It never recursively interprets extracted bytes.
- `{type: "extract-bsa104", source: "archive-id", container: {member: "Data/Example.bsa", bytes: 12345, sha256: "<64 lowercase hex characters>"}, member: "meshes/example.nif"}` explicitly selects one internal member of a BSA-104 container within a locked Nexus/HTTPS ZIP, 7z or RAR download. The container has its own exact size/hash; the output locks the inner file's exact uncompressed size/hash. Both member paths follow the canonical recipe path rules. A recipe may use at most 64 distinct containers totaling 20 GB of staging data; each container is 36–4,294,967,295 bytes and each inner output is at most 1 GB. Conflicting declarations for the same container are rejected. Only the [documented BSA-104 subset](bsa-inspection.md) is accepted. This is exactly one declared container level; direct owned-game BSA inputs, BSA writing, BA2, BSA 103/105, arbitrary nested archives, FOMOD execution, binary patches and arbitrary text substitution remain unsupported.
- `{type: "mo2-config", gameEdition: "Steam", executables: [...]}` generates only `ModOrganizer.ini` from bounded, relative executable declarations and recipe game/launch fields. `gameEdition` accepts `Steam` or `GOG` matching the target game requirement; executable entries may declare `steamAppId` matching the supported target game and its Steam requirement. Both fields are optional for legacy recipes, whose exact generated bytes remain unchanged. It has no source or static output fingerprint. The materializer computes the exact destination-specific bytes/hash before writing and records them in the receipt after verification. An empty, fingerprinted `portable.txt` output is required. See the [complete generator contract](native-mo2-configuration.md), including serialization, size bounds and unsupported settings.

Outputs must include `ModOrganizer.exe`, `ModOrganizer.ini`, the declared profile's `modlist.txt` and `plugins.txt`, and the target game executable beneath `launch.gameRoot`. Mod priorities, disabled entries and plugin order are carried by the exact profile files. Where the manager/game derives order from modification times, declare the corresponding winning plugin timestamps too. Neither order nor timestamps are inferred from source order. Final-file verification checks each static or derived output fingerprint after reconstruction. Save paths may never be claimed as owned recipe outputs.

## Creator commands

Place reviewed bundled files in a private directory, named by their SHA-256 hashes. A recipe with no payloads can use an empty directory. Commands never replace an existing package:

```powershell
node scripts/native-package.mjs pack recipe.json private-payloads example.loadstone
node scripts/native-package.mjs inspect example.loadstone
```

The compiler validates and hashes all bundled bytes, creates the output exclusively, and re-inspects the finished archive. Changed inputs or mismatched hashes fail. It refuses output paths inside the payload directory. Keep personal inventories, local manifests and unreviewed packages under ignored `test-results/`; do not commit them.

The desktop guide and creator tools use this materializer; reconstruction does not establish playability.

Preserve the existing launch/shortcut/removal ownership checks. Prove actual clean installation and gameplay before publishing the three featured recipes or assigning 1.0.

# Native reconstruction

Canonical source: `docs/native-reconstruction.md`

The native materializer creates the exact outputs of a validated `.loadstone` recipe from local owned-game files, local prerequisites, ZIP/7z/RAR archives and permitted bundled payloads. The desktop can [acquire declared original archives](native-downloads.md), and the materializer can [generate bounded MO2 configuration](native-mo2-configuration.md) for the new destination. Players can use [guided installation in Discover](native-guided-install.md); creator tooling remains available through the CLI and Settings. Completed candidates can be explicitly admitted to the [native library](native-library.md) for launch and shortcut controls. Reconstruction itself does not perform TTW conversion, apply arbitrary transforms, migrate all profile/tool settings or launch a game. Do not advertise a playable featured list from a fixture result.

## Desktop creator workflow

Switch to the live workspace and open Settings → Reconstruct a local candidate. Select the package, its private local-inputs JSON (described below), and an existing parent directory. Review the recipe name, output count, storage requirement and newly generated destination. **Build candidate** starts input verification and reconstruction; the renderer cannot supply a replacement path or arbitrary recipe. The main process binds the reviewed recipe fingerprint to the materializer.

If the inputs include 7z/RAR archives or request downloads, select a trusted local **7-Zip x64 26.04 or newer** `7z.exe` with its matching `7z.dll`. Downloads are conservatively prepared for any supported archive signature; a ZIP download still uses the built-in ZIP reader. The review shows the selected version. The app retains the tool identity between review and build and rejects changes. Cancelling this picker creates no job. Recipes and private-input files cannot nominate an executable; selection is through the native picker. No 7-Zip binary is bundled, automatically downloaded or installed.

Progress and cancellation appear in Downloads and this Settings card. Success says **Files verified · Launch untested**. Downloads offers **Review for My library** for the exact completed folder. Native candidates are not automatically registered or given shortcuts; explicit library review is separate. Native builds, library verification, other installations/removal and engine preparation cannot start over one another; the close guard keeps Loadstone open until selection/build/cancellation finishes.

Active builds distinguish archive acquisition, source-file checks, archive-structure checks, writing outputs and final-file verification. The display shows completed files within the current stage and bytes in the current file, so large files can show activity before a file-count increment. Writing every output does not finish the build: final hashes must still pass. Byte updates are throttled; these are measured counts, not an overall time estimate. The local-only CLI reports materializer phase changes and bounded periodic activity without source paths. Reading/validating the package itself still precedes this phase reporting.

Phase activity exists only in memory and is absent from persisted build history and diagnostic exports. Restarted builds keep the existing interrupted-state behavior, rather than presenting stale phase progress as active work. Cancellation and failure still preserve any partial candidate.

`native-builds.json` in the local app-data folder retains up to 100 build records, including destination, recipe fingerprint, progress and status. It contains no credential, source archive paths, local-input map or raw tool output and is excluded from diagnostic exports. Invalid/newer history is preserved and refused, rather than silently reset. Active records become `interrupted` after restart without resuming work. Cancelled, failed and interrupted candidates offer [explicit recovery review](native-build-recovery.md): reselect the same recipe and inputs, reuse matching files and retain conflicts before rebuilding them. Resume updates the same history entry. [Native version updates](native-updates.md) use a separate candidate; build-history management remains unfinished. Failed writes or external history changes stop new work and require restart.

## Local command

```powershell
node scripts/materialize-native.mjs candidate.loadstone private-inputs.json C:\LoadstoneReview\NewCandidate
# Include this explicit operator-selected tool for 7z/RAR inputs:
node scripts/materialize-native.mjs candidate.loadstone private-inputs.json C:\LoadstoneReview\NewCandidate --sevenzip C:\Tools\7-Zip\7z.exe
```

The destination's parent must already exist; the destination itself must not. The private JSON input file has two maps: `games` maps each required game ID to its installed source folder; `archives` maps each archive source ID from the recipe to a locally downloaded ZIP, 7z or RAR file. When the recipe declares local prerequisites, add a `prerequisites` map from each prerequisite ID to its prepared source folder. All declared prerequisite files are hashed before reconstruction; the app never runs the instructions URL or a conversion program. Paths must be absolute. Keep this file under ignored `test-results/` and do not publish it. It contains no Nexus credentials or runtime command arguments.

For example, a private input file can contain:

```json
{
  "games": { "fnv": "C:/OwnedGames/Fallout New Vegas" },
  "archives": { "example-source": "C:/ModDownloads/example.zip" }
}
```

These example paths are illustrative. The executable, required game files and archives must match the actual recipe's byte lengths and SHA-256 hashes; having a folder with the expected name is insufficient. Storefront/license eligibility remains a separate release requirement.

In the desktop workflow only, an archive map value may instead be `null` to request acquisition of that recipe source. Every source ID must still appear exactly once; omitted or extra IDs are rejected. The CLI remains local-only. See [original-source downloads](native-downloads.md) for cache, network and membership behavior.

## Data preservation and verification

All requirements and archive hashes are checked before creating the installation directory. ZIP, 7z, RAR4 and RAR5 inputs are recognized by their signatures, allowing mislabeled original filenames without renaming them; signatures never replace hash or structural validation. Archive paths, links, duplicate/colliding names, encrypted/unsupported entries, required members and declared sizes are checked in advance. Available destination space must cover expected outputs, recipe metadata and a 64 MB reserve. Archive inventories are limited to 500,000 entries and 100 GB declared uncompressed content; local archives are bounded to 50 GB.

For upstream ZIP sources, backslashes are normalized to forward slashes before structural checks and during extraction, matching the source mapper's member paths. Mixed-separator aliases, case collisions and file/directory overlaps are rejected before creating a destination. Recipes still use canonical `/` member paths, and native `.loadstone` package entries retain strict naming. Original archives are read unchanged; this compatibility rule does not permit arbitrary path cleanup or remove traversal checks.

7z/RAR reconstruction uses the same validated adapter as [source comparison](installed-inventory.md). The external tool runs without a shell and emits file content to stdout; it never receives output paths. Loadstone waits for disk writes before reading more data, checks exit status and input identity, and closes the child before reporting failure or cancellation. Tool diagnostics do not enter build history. 7-Zip 26.04 with `zlib.crc32` uses one pass for eligible 7z archives with per-member CRCs and at most 20 GB total content. Every boundary, including unselected members, is CRC-checked. Up to 100,000 selected members are supported in that pass. Other versions, RAR and ineligible 7z archives read each selected member with literal selectors: at most 10,000 members and 20 GB selected content per archive. This fallback can be slow for solid archives. Single-pass extraction has a five-minute limit; fallback reads have a ten-minute limit per member. These are experimental creator limits, not general archive support guarantees.

Destinations cannot overlap selected game inputs, source archive/package folders, the selected tool directory, the application, system folders or additional protected roots supplied by the caller. Redirected directories are rejected; existing destinations require a separate bound recovery review in the desktop builder. New directory creation is exclusive; output files use exclusive creation. The materializer never modifies source game files or downloads, executes archive content or writes save paths.

Each output stream is bounded and hashed, then all final files are re-hashed before success. Static outputs use recipe fingerprints; generated MO2 configuration uses the destination-specific fingerprint computed before writing. The new directory contains `.loadstone-recipe.json` and `.loadstone-native.json`. The receipt records the recipe fingerprint, generated-configuration fingerprints when present, progress and one of `materializing`, `verified`, `failed` or `cancelled`. `verified` means reconstructed bytes matched the static or derived expectations; `launchVerified` remains false.

Cancellation or failure retains the candidate directory and receipt. A hard process kill may leave a `materializing` receipt and an incomplete file; desktop history marks the build interrupted after restart. [Resume review](native-build-recovery.md) checks retained bytes, preserves conflicting files in a unique recovery folder and revalidates every final output. The writer does not recursively delete failed setups or continue automatically after a restart.

These checks supplement standard Windows access controls; they are not a sandbox for an actively hostile process racing filesystem changes. Keep source files and the new destination settled during reconstruction.

## Nested BSA 104 files

An explicit `extract-bsa104` action can reconstruct loose files from a BSA container inside an original ZIP, 7z or RAR source. The recipe independently locks the outer archive, its BSA member and the final inner file. The installer validates the complete outer archive structure, stages only the declared containers, verifies their full hashes, and checks every BSA member and selected output before creating or changing installation files. Ordinary `extract` actions keep their direct-member meaning.

Staging uses one new directory beneath the operating system's temporary directory and numbered files, never archive-supplied filesystem paths. Up to 64 containers and 20 GB of staging bytes are accepted per recipe. The temporary volume needs the declared container bytes plus a 64 MB reserve; destination space is checked separately. Each container follows the [BSA reader's format and decompression limits](bsa-inspection.md). A compressed or shared member is streamed through an awaited consumer, then the installation writer verifies its exact output bytes/hash and applies any declared timestamp. No archive code runs.

Handled success, cancellation and failure close the readers/writers and remove the operation's ordinary staging files. Cleanup checks directory/file identity, performs no recursive deletion and preserves changed or unfamiliar staging contents. A hard process termination can leave temporary containers behind; restarting builds new staging after a fresh source/recovery review and does not blindly purge earlier temporary folders. Failed installation outputs and user data retain the existing receipt/recovery behavior. Resume reuses verified outputs; repair preserves conflicts and personal configuration through the same review path as other actions.

Synthetic tests cover ZIP, solid 7z and RAR5 outer archives, mixed direct/nested outputs, compressed/empty/shared BSA members, exact timestamps, invalid containers and inner members, unsafe trailing archive entries, resource limits, failed staging writes, cancellation, resume and repair. Actual Electron tests exercise reviewed ZIP and RAR5 reconstruction through the bridge and are also run against the staged executable. The CLI inventory remains evidence only; automatic nested-source ledger mapping is separate work.

## Acceptance remaining

Complete real provider-download acceptance, conversion, profile/tool configuration reconstruction, real version-update and maintenance acceptance. Creator reconstruction is exercised through real Electron with original synthetic ZIP, solid 7z and stored RAR5 inputs, including cancellation, failed writes and tool replacement. The RAR5 fixture is generated from the [published format](https://www.rarlab.com/technote.htm), without third-party archive contents or encoder code. Clean-machine installation and gameplay acceptance remain unfinished. The separate package inspection card stays read-only.

Completed candidates with generated portable MO2 configuration may be explicitly reviewed and registered in the [native library](native-library.md). Registration adds launch and shortcut controls after file and local-profile checks. Separate [removal review and confirmation](native-maintenance.md) limits deletion to unchanged recipe files and retains user data; these controls do not certify gameplay.

# MO2 configuration

Canonical source: `docs/native-mo2-configuration.md`

Experimental creator support: a `mo2-config` action generates a new `ModOrganizer.ini` bound to the chosen candidate folder. It does not import an existing INI, copy account settings, run MO2 or certify a playable list. Existing copy/extract recipes remain supported unchanged; older Loadstone builds reject this new action.

## Recipe declaration

This is the only output kind without a static `bytes`/`sha256` pair or a source reference:

```json
{
  "path": "ModOrganizer.ini",
  "action": {
    "type": "mo2-config",
    "gameEdition": "Steam",
    "executables": [
      {
        "title": "New Vegas",
        "binary": "Game/FalloutNV.exe",
        "workingDirectory": "Game",
        "steamAppId": "22380"
      }
    ]
  }
}
```

There must be 1–64 entries. Titles are unique without regard to case, trimmed, well-formed text of 1–100 characters without controls. Each binary is a safe, relative, declared `.exe` output. Its working directory is its exact relative parent, or `.` for an executable at the candidate root. The entry whose title exactly matches `launch.executable` must be under `launch.gameRoot`. The recipe must also declare an empty `portable.txt` output with the SHA-256 of zero bytes. A file cannot shadow `downloads`, `mods`, `profiles`, `overwrite` or `webcache`.

An entry may optionally declare 1–16 arguments as `[{"type":"path","path":"Game/Data"}]`. Each path must name a declared output or an ancestor directory (or `.` for the candidate root). They are bound to the destination and individually quoted for Windows command-line argument boundaries. This supports Explorer++ opening the local virtual game-data folder without retaining a creator path. Arbitrary literal arguments/flags, INI keys, scripts, environment variables and external paths are unsupported. Supporting an entry does not run it during reconstruction.

### Game edition

New recipes should declare `gameEdition` as `Steam` or `GOG`, matching the `store` on the requirement for `game.id`. For TTW this is the New Vegas requirement, even when the Fallout 3 requirement uses another store. Other values and mismatched stores are rejected. This writes `General/game_edition` so MO2 can select the edition without its first-run dialog. Launch checks reject a changed or missing declared edition; Qt rewriting its quoted value is accepted.

The field is optional only for compatibility with existing recipes and reconstruction receipts. Omitting it preserves the original generated bytes exactly and can leave MO2 asking for an edition at first launch. It does not silently upgrade an existing candidate. Recipes using the field have a different canonical fingerprint and are rejected by older Loadstone implementations. Build a new candidate from the revised recipe; retain any existing saves and configuration. This declaration does not certify GOG runtime support or convert game files between stores.

### Executable Steam app ID

An executable may declare `steamAppId` as a string matching Loadstone's supported target game: `22380` for New Vegas/TTW, `489830` for Skyrim SE or `377160` for Fallout 4. The target game's requirement must use `store: "steam"`; TTW's Fallout 3 requirement does not determine this value. Other IDs, numbers, empty values and GOG requirements are rejected. Regional app IDs are not supported by this declaration.

This writes that executable's `steamAppID` setting for MO2's Steam launch context. The field is optional to preserve existing generated bytes and receipts. Adding it changes the recipe identity and requires a new candidate; it does not change an existing receipt or grant game ownership. Native launch rejects a changed or missing declared app ID. A private TTW check found this setting in the installed baseline but absent from earlier generated configuration; actual launch and recording outcomes are tracked in the [acceptance record](native-steam-acceptance.md).

## Deterministic rendering and verification

The canonical recipe fingerprint locks all generator inputs. Before creating a destination, the materializer renders UTF-8/LF configuration for that absolute Windows drive path and computes the resulting exact byte length and SHA-256. Stream verification and the final on-disk pass use this derived fingerprint. The receipt's `generatedConfigurations` array records `{path, generator, bytes, sha256}` without embedding the destination. Static copy/extract outputs retain their existing exact fingerprint contract. A `mo2-config` output cannot also declare a static fingerprint: rendered bytes depend on the destination.

The generator produces these sections in order, with a blank line between sections and a final LF:

- `General`: game name (`TTW`, `New Vegas`, `Skyrim Special Edition` or `Fallout 4`), local game path, selected profile, `first_start=false`, then `game_edition` as a quoted Qt string when declared.
- `Settings`: local base, downloads, mods, profiles, overwrite and webcache paths; `profile_local_inis=true` and `profile_local_saves=true` defaults.
- `customExecutables`: array size, then each entry's title, local binary, local working directory and arguments (empty when omitted, otherwise a space-separated sequence of quoted local paths), followed by `steamAppID` when declared, preserving declared entry order.

Paths use `/`. Qt string values are double-quoted, escape backslash and quote, and double a leading `@`. Game path and selected profile use `@ByteArray(...)` with every UTF-8 byte encoded as lowercase `\xNN`. The implementation in `electron/native-mo2-config.cjs` defines the exact serialization; byte changes require a new generator action identity, not a silent change to an existing recipe's meaning.

Generated files are limited to 1 MB. Package inspection reserves that allowance in `installBytes` and exposes `generatedConfigurations`; the desktop explains the allowance. Destinations for this action are limited to local Windows drive paths of 2,048 characters without controls or literal `%BASE_DIR%`, which MO2 would interpret as a variable. Normal materializer protection, exclusive creation and cancellation rules still apply. Required empty MO2 state directories are created inside the candidate. A cancelled or failed candidate is retained.

## Scope and acceptance

This creates a fresh manager configuration. It does not preserve personal interface preferences, plugin-specific settings, external tools, account data or recent directories. Any behavior required by a featured baseline must be identified and modeled before claiming equivalence. Existing profile `settings.ini`, game INIs, plugin configuration and tools needing literal arguments/flags still require review. In particular, the defaults above do **not** prove that an existing profile uses local saves: profile-specific flags can override defaults. Native candidates remain **Files verified · Launch untested**, outside the playable library.

Absolute paths are deliberately bound at installation. Moving a finished candidate does not automatically update them; rebuild into a new destination until relocation/repair is implemented. This action does not patch arbitrary existing text, transform mods, convert TTW, download sources or create shortcuts.

Path and executable semantics were checked against the [ModdingLinked MO2 settings implementation](https://github.com/ModdingLinked/modorganizer/blob/9c130cb/src/settings.cpp), [MO2 executable loading](https://github.com/ModOrganizer2/modorganizer/blob/master/src/executableslist.cpp), and [Qt INI serialization](https://github.com/qt/qtbase/blob/6.7/src/corelib/io/qsettings.cpp). The original generator does not copy upstream implementation code. MO2's mod-directory setting is `mod_directory` (singular); installed inventory now honors it.

MO2's [process launcher](https://github.com/ModdingLinked/modorganizer/blob/9c130cb/src/spawn.cpp) uses the executable's Steam app ID for its child environment. Native launch validation reads the required General, Settings and customExecutables sections, retaining strict alias/duplicate/path checks. Unrelated plugin and UI section values are left alone, including MO2's normal `Python%20Proxy` persistence key. Profile validation reads its General section separately.

Tests cover different destinations, non-ASCII and INI delimiter encoding, invalid references and fields, final-file tampering, destination refusal and the real Electron review/build/restart workflow. Inventory and existing launch-layout checks decode the generated UTF-8 byte arrays and quoted strings; unrelated binary INI state is not decoded or exported. A private interoperability check also read synthetic generated configuration through Qt 6.7.1's actual `QSettings`, including UTF-8 byte arrays, literal `@`, quoted delimiters and executable arrays. This verifies serialization, not MO2 launch or gameplay.

# BSA inspection & mapping

Canonical source: `docs/bsa-inspection.md`

The experimental creator command reads a local **BSA version 104** container and produces a private inventory of its normalized member names, exact uncompressed sizes and SHA-256 hashes:

```powershell
node scripts/inspect-bsa.mjs C:\CreatorCache\original.bsa C:\CreatorReports\bsa-inventory.json
```

Choose a new report outside the archive's directory. The command never extracts payload files, executes content or modifies the archive. Ctrl+C cancels without a final report. Keep reports private: member names can disclose installed content even though the report omits the local archive path.

The archive itself is hashed before inspection. All index, member, decompression and input-stability checks must pass before a report is returned. Exact shared data extents are supported; partially overlapping extents and conflicting compression declarations are rejected. Embedded filename blobs are validated but are not used as member paths: optimized archives may share one blob across several indexed names. Names use canonical forward slashes; duplicate/case-colliding paths, traversal, Windows special names and file/directory overlap are rejected.

This initial reader accepts the version-104 layout used by Fallout 3/New Vegas: a 36-byte header, folder/file name tables, printable ASCII names, optional zlib compression, per-file compression toggles and optional embedded names. It accepts archive flag bits `0x01`, `0x02`, `0x04`, `0x80` and `0x100`, with both name tables required. Other layouts/flags, non-ASCII names, BSA 103/105, BA2 and archive writing are unsupported. Rejection means the reader cannot safely inspect that variant, not that the game archive is necessarily corrupt.

Limits: 4,294,967,295 input bytes, 64 MiB metadata, 100,000 folders, 500,000 files, 1 GB per uncompressed member, 20 GB total logical member content (including shared copies) and five minutes per inspection. Hashing streams have bounded buffers; declared sizes, zlib input consumption and output counts are verified. The reader uses the same open file handle throughout and checks file identity afterward.

This report is **source evidence only**. It does not change the ZIP/7z/RAR ledger or automatically produce a recipe. To establish an upstream source chain, separately verify the outer download archive, its exact BSA member hash and the desired internal member hash. Compare the installed file's complete size/SHA-256; a similar name or image is insufficient. A reviewed recipe can use the explicit [`extract-bsa104` action](loadstone-format.md#outputs-and-actions) for [bounded nested-BSA reconstruction](native-reconstruction.md#nested-bsa-104-files). Transformed-file reproduction, rights review and real installation acceptance remain separate work. No game or mod data is bundled by this command.

The JavaScript implementation and synthetic fixtures are original. Format semantics were checked against Wabbajack's pinned [104/105 reader](https://github.com/wabbajack-tools/wabbajack/blob/4.2.3.0/Wabbajack.Compression.BSA/TES5Archive/Reader.cs), [folder records](https://github.com/wabbajack-tools/wabbajack/blob/4.2.3.0/Wabbajack.Compression.BSA/TES5Archive/FolderRecord.cs) and [file records](https://github.com/wabbajack-tools/wabbajack/blob/4.2.3.0/Wabbajack.Compression.BSA/TES5Archive/FileRecord.cs). Loadstone deliberately supports a narrower format subset.

## Nested source mapping

The separate creator command extends a private [source ledger](installed-inventory.md) with exact nested matches:

```powershell
node scripts/map-bsa-sources.mjs private-mapping.json new-private-bsa-mapping.json --mod "Example container mod" --7zip C:\Tools\7-Zip\7z.exe
```

Repeat `--mod` for other exact inventoried mod names. The selected mods must contain inventoried `.bsa` files and have original archive candidates in the ledger. Disabled mods can supply containers without being enabled. The optional `--7zip` is required for 7z/RAR candidates; ZIP comparison uses the built-in reader. No tool or original archive is downloaded by this command.

The mapper independently rehashes each selected original archive and validates its complete structure. It hashes candidate BSA members and compares their full size/SHA-256 with the installed BSA inventory. Only then does it inspect the matching local BSA, rechecking the complete container fingerprint and hashing its internal contents. The local file is a read-only witness of the verified original member; nothing is staged or extracted. It compares inner content with all managed mod-file fingerprints in the accepted ledger, including disabled mods, and excludes local `meta.ini`. It does not rehash every loose installed target during this pass, nor map game/root/profile/overwrite records.

Each matched file receives a separate `bsaSourceMatches` array. A reference records `archiveSha256`, `container: { member, bytes, sha256 }`, the inner `member` and the number of byte-equivalent inner members (`equivalentMembers`). The representative is the lexicographically first normalized inner path per container and content fingerprint. The original archive's fingerprint and available provider hints appear in `bsaMapping.sources`; provider hints still require review. These references supply the fields for a reviewed `extract-bsa104` action once a recipe source ID is assigned. They do not generate or approve a recipe.

Existing `sourceMatches`, the direct `mapping` report, mod states and other inventory records remain intact. `bsaMapping` separately reports nested matches, newly matched files and the combined unique file totals. Re-running the command replaces the nested extension from fresh checks without multiplying old references. A fresh direct archive-mapping pass clears the old nested extension, which must then be recomputed. Failed archives or containers produce unresolved issues; no partial matches from a failed inspection are accepted.

Limits: 64 selected containers, 20 GB total container bytes, 20 GB combined successfully inspected logical content, 1,000 candidate archive paths and 500,000 nested match references, in addition to the existing archive/BSA reader limits. ZIP and per-member 7z/RAR comparison retain their 1 GB member limit; eligible 7z archives can use the existing bounded single-pass reader for larger members. Other BSA versions and arbitrary nesting remain unsupported.

The command locks the input ledger, referenced inventory and optional source hints, checks them again before writing, refuses existing report paths and keeps reports outside installation/download roots. Ctrl+C cancels without a final report. Reports contain private paths and installed-content names: keep them outside public source. Matching bytes establish source evidence only; source rights, typed transformations, recipe validation and actual reconstruction/gameplay acceptance remain required.

# Live catalog manifests

Canonical source: `docs/manifests.md`

Discover in live mode supports importing a local JSON manifest. Place the original `.wabbajack` archive beside it (or in a declared subfolder). Loadstone keeps manifest metadata in its local `live-catalog.json`; it does not redistribute the archive or its mods. Imports remain separate from demo installations.

Schema 1 requires these fields, with unknown fields rejected:

- `schemaVersion`: `1`; `id`: a stable lowercase slug (3–64 characters).
- `name`, `version`, `description`, `author`, `website` (HTTPS).
- `game`: `id` (`fnv`, `skyrimse`, or `fallout4`), `versions` (human-readable labels), `executableHashes` (supported lowercase SHA-256 values), `requiredFiles` (relative file paths and their `sha256`, including required DLC masters).
- `storage`: positive integer `downloadBytes` and `installBytes`, including temporary space needed by the list. These are author declarations; preflight checks available space against their combined total.
- `archive`: relative `file` ending in `.wabbajack`, `sha256`, and original HTTPS `source`.
- `launch`: `manager: "mo2"`, `profile` (a single directory name), `executable` (MO2 executable title), and optional `gameRoot` (a relative folder within the installed profile, such as `Stock Game`). No shell commands or installation recipes are accepted.
- `credits`: entries with `name`, `author`, HTTPS `source`, and a `license` or distribution-permission statement. Declared permissions require human review before public distribution.

Preflight streams file hashes, checks required game files and archive integrity, rejects game/system/Loadstone folder overlap and nonempty destinations, and checks writability and free disk space. It does not create an install or modify the game. Steam discovery reads local library and app metadata and confirms the executable exists; it does not assert ownership from an install directory. GOG and other installations can be selected manually.

Installation requires the verified engine, successful live preflight and source access. A valid manifest alone does not make a setup installable. No real curated list is bundled yet.

Preflight also reads the archive's actual `modlist` metadata. It checks game identity, required engine version, MO2/profile output files, bounded sizes, safe and unique Windows output paths, and declared storage against the archive's totals. Unknown download providers and lists requiring additional games are identified as unsupported. A verified engine is asked which game folder it would use; a different selection blocks installation rather than silently using another copy of the game.

The parser was checked against the locally cached Viva New Vegas 11.8.26 archive: 153 source archives and 17,630 output files. The pinned 4.2.3.0 CLI was also run to confirm its actual Fallout 4 and New Vegas selections. These are read-only compatibility checks, not evidence of a successful installation or permission to redistribute the list.

The pinned [Wabbajack install command](https://github.com/wabbajack-tools/wabbajack/blob/4.2.3.0/Wabbajack.CLI/Verbs/Install.cs) accepts `-w/--wabbajack`, `-o/--output`, and `-d/--downloads`. The runtime and command interface are verified; protected authentication and durable job recovery are implemented; full real-list installation acceptance remains outstanding.

## Updating an imported setup

Keep the same stable ID and use a different version label. Add optional schema-1 metadata (required when replacing an imported version):

```json
"update": {
  "fromVersions": ["1.0"],
  "saveCompatibility": "new-game-required",
  "notes": "Start a new game. Keep version 1.0 for existing saves."
}
```

Allowed compatibility values are `compatible`, `new-game-required`, and `unknown`. These are creator declarations, not Loadstone guarantees. Notes must explain the migration requirements. Version labels are opaque: Loadstone does not infer ordering from dates or semantic versions. Reimporting the same version is rejected, including altered archives; publish a new version instead. A game change under the same ID is rejected.

Import presents the old/new versions, creator/source and save guidance for confirmation, then checks the manifest has not changed before saving. Existing jobs retain their own manifest snapshots. Install a replacement in a separate empty folder; Loadstone keeps the prior profile, settings, saves and custom mods available for rollback. It does not migrate saves or customizations automatically. Installed versions appear in Library. Older failed jobs retry their owned archive using their original manifest, even after the catalog changes. If that archive is missing and the original manifest is no longer imported, restore the exact owned archive before retrying.

## Isolated game layouts

A creator can declare an existing Wabbajack Stock Game layout:

```json
"launch": {
  "manager": "mo2",
  "profile": "My setup",
  "executable": "New Vegas",
  "gameRoot": "Stock Game"
}
```

The Wabbajack list must itself build and configure that layout. Adding this field does not copy a game, run a patcher or convert an existing list. Archive preflight requires the supported game's executable among the declared outputs under that folder. Completion, profile checks, launch and shortcut creation require the installed folder and game executable to exist without redirection, MO2's General/gamePath to resolve to that folder, and the selected launch entry to point inside it. Missing, duplicated or mismatched gamePath settings fail verification. Ordinary, quoted and backslash-escaped @ByteArray path forms are recognized.

This follows the upstream [Stock Game authoring model](https://wiki.wabbajack.org/modlist_author_documentation/Keeping%20the%20Game%20Folder%20clean.html): game preparation belongs in the creator's compiled list and must be validated for the selected storefront. Patches, required plugins and clean-machine gameplay still need acceptance evidence; a directory match does not prove those requirements.

The field is optional for existing schema-1 manifests and saved installations. Its absence preserves legacy behavior and makes no isolated-layout guarantee. The cached Viva New Vegas candidate is not a Stock Game list; merely adding gameRoot causes preflight to reject it. A suitable creator-authored variant and actual install-to-play acceptance remain required for one-click support.

# Brand system

## The mark

`public/brand/mark.svg` is the single editable geometry source. The three faces describe one solid shape, with an open counter and a restrained edge highlight. Keep its proportions, negative space and colors together. Do not add extra compass points, bevel filters, outlines or tiny ornaments.

# Verification checklist

Canonical source: `docs/review.md`

This build includes the live installer and maintenance features developed after the original demo. It is unsigned and remains a private developer preview. A real supported install-to-play run, clean Windows/Steam acceptance, Nexus registration and distribution/asset license review are still required before public release. Original source is licensed under GPL-3.0-or-later; new builds include its license offline.

## Walkthrough

1. Start with a fresh test workspace. The welcome screen offers live setup or the fictional demo; neither starts a download automatically.
2. Explore the demo: Discover filters/details, install planning, Downloads pause/cancel/retry, Library actions, settings persistence and reduced motion. Demo activity must remain separate from live state.
3. In the live workspace, prepare the pinned engine in Settings and import a compatible creator manifest/archive. Check the game and destination. Failed compatibility or account checks must prevent installation.
4. Connect Nexus only through Settings in your local app. Do not put keys in chat, manifests or reports. Lists requiring automatic Nexus downloads currently need Premium, and a conflicting saved Wabbajack login must be resolved in that application.
5. With an accepted real list, exercise download/install, failure/retry, output verification, profile launch, shortcut repair, version coexistence and save-preserving removal. These are required acceptance steps, not a claim that they have already passed.
6. Export diagnostics and confirm build identity. Ordinary closes during installation, removal or engine preparation should keep the operation visible and offer minimization. Idle closes should exit cleanly.
7. In Settings, inspect a native package, then reconstruct a synthetic local candidate with the matching private inputs JSON. Confirm the new destination and prerequisite summary before starting. Check cancellation, restart history and **Files verified · Launch untested**; build completion must not automatically add a library entry. Explicitly review/register a launchable synthetic candidate in My library; check restart persistence, save isolation, file changes, redirected folders and fixture-only Desktop/Steam shortcuts. No synthetic executable may be run. Use fixtures outside real game, Desktop and Steam folders.

For current source with native downloads, also review the source hosts/cache/bytes for an archive input set to `null`. Exercise acquisition, hash failure, cancellation, verified-cache reuse and final reconstruction. Keep fixture network responses synthetic; separately record any real provider/account acceptance. Never put a key or signed URL in a recipe. The older recorded 0.3.0 binary does not contain these later changes.

The existing VNV archive needs additional game preparation. Read [the real preflight findings](vnv-acceptance.md) before using it as an acceptance candidate. An isolated-layout declaration does not convert an archive into a Stock Game list.

## Reproduce package verification

Run `pnpm check`, `pnpm test`, then `pnpm package` from a clean commit. Set `LOADSTONE_TEST_EXE` to `release/win-unpacked/Loadstone.exe` and run the complete staged-executable test selection in `.github/workflows/windows.yml`, including native installation, library, repair, version updates and manual downloads. Clear that environment variable, then run `node scripts/verify-portable.mjs` to exercise the actual self-extracting executable. The script derives its filename/version from package metadata and checks the full license and scope offline. It records the artifact's SHA-256, size and checked workflows under ignored `test-results/`. Optional package/evidence directory arguments preserve previous artifacts; see [private preview packaging](private-preview.md).

Use a dedicated `LOADSTONE_DATA_DIR` for manual review. This isolates settings and credentials, but does not redirect Desktop or Steam operations. Automated shortcut tests use explicit temporary targets. Do not point a test workspace at data you need to preserve.

The original [0.1.0 review](review-0.1.md) is historical evidence for the demo-only release. Its screenshots and claims do not certify the newer live installation features. See [Steam depot verification](steam-release.md) for the separate directory build and actual-client acceptance requirements.

For native removal, use synthetic candidates and redirected Desktop/Steam fixtures. Exercise review cancellation, explicit confirmation, modified/untracked-file preservation, failure before the durable record, interrupted removal and restart/resume, blocked shortcut cleanup and retry. Verify source-game and save canaries remain unchanged; never use a live candidate for destructive fixture acceptance.

For native build recovery, interrupt a synthetic build, restart, select the same recipe/inputs and review resume. Dismiss first and verify no candidate changes. Confirm reuse without rewriting matching files, retained copies of conflicts, untouched untracked/save canaries and one persistent history entry. Test changed metadata/roots/files after review, redirected folders, failed input verification, a failed write after a conflict was retained, repeated cancellation and ZIP/7z/RAR reconstruction. Final verification must still hash every output. Actual games and managers remain closed; no fixture executable is run.

For guided native installation, use Discover → Open .loadstone with synthetic owned-game discovery and native pickers. Verify required inputs, changed selections invalidating review, original-download/local-archive choices and no JSON-file requirement. Confirm Downloads tracks cancellation and guided resume in the same job/folder. Review the completed folder for My library, cancel admission first, then confirm and verify restart persistence. The draft must disappear after restart while completed history and library entries remain. Run `tests/native-guide-electron.test.mjs` against both local Electron and the staged executable; no synthetic executable may be launched.

For installed native repair, modify/delete synthetic recipe outputs and add save/configuration canaries after registration. Review the exact original recipe, verify preservation defaults and confirm repair. Check retained originals, unchanged matching-file identities, save/profile preservation, explicit configuration restore, cancellation, failed writes after retention and restart recovery. Fail final state persistence and ensure launch stays disabled until a fresh review succeeds. Run `tests/native-repair-electron.test.mjs` against local and staged Electron. Real installed setups may be reviewed read-only; never use them for destructive fixture acceptance.

For native version updates, register a synthetic setup, change its configuration and add a save canary. Select a different version of the same setup, verify both version labels and new save guidance, then build and admit the independent candidate. Assert the complete original tree and entry remain unchanged, the new version uses fresh recipe settings and no copied saves, and both entries survive restart. Reject mismatched setup/game/variant, same-version packages, overlapping destinations and changed original metadata/registry. Cancel or fail the new build and resume its exact candidate without touching the old version. Run `tests/native-update-electron.test.mjs` against local and staged Electron. Real version-to-version gameplay and save compatibility remain separate acceptance.

For manual Nexus downloads, use synthetic archives and intercept the browser opener. Verify exact game/mod/file routing, default browser mode without Premium, pending counts, wrong-length/hash rejection, cancellation with unchanged previous selection, explicit cache reuse and rechecking changed bytes at installation. Reject arbitrary URLs, undeclared sources and stale drafts. Run `tests/native-manual-electron.test.mjs` locally and against the staged executable. The intercepted opener does not replace a separate real authorized Nexus website/account/download acceptance.

# Path to 1.0

Canonical source: `docs/1.0-plan.md`

The target is a usable Windows Player Tool that installs, maintains, and launches a curated Bethesda setup from original download sources. A polished dummy catalog alone does not satisfy this goal. Version 1.0 will only be assigned after the real install-to-play path and the release requirements below are proven.

## Required product behavior

1. Loadstone can distinguish demo and live workspaces, with no simulated checks masquerading as real installation results.
2. A versioned setup manifest identifies a real game, supported versions/DLC, source downloads, hashes, author credits, license information, required storage, and the intended launch profile. Imports cannot execute arbitrary shell recipes.
3. A real installation adapter validates the selected game, destination, disk space, engine, and authenticated source access. Download/install progress reflects actual work; interruptions have an explicit recovery path.
4. A completed install is verified against the produced profile. The library launches the correct real MO2 profile/script extender. Desktop and local Steam shortcuts work and can be repaired without replacing unrelated entries.
5. Removal is limited to owned setup files, with save preservation by default. Updates declare save compatibility and preserve user choices or offer a recoverable fresh install.
6. Nexus credentials stay local and protected, never appear in logs, and follow membership restrictions. A public application needs Nexus registration; developer testing access must not be advertised as approved public access.
7. The Windows package has reproducible build instructions, versioned state migration, diagnostics, privacy/support documentation, license notices, and passing real Electron tests. The Steam depot build is distinct from the portable local preview.
8. A clean Windows review verifies at least one real supported game/list end to end, including restart, failed download/retry, launching, shortcuts, maintenance, and removal. Fixture tests supplement this review; they cannot replace it.
9. The repository is ready for an open-source release: accurate public-facing README, reproducible contributor setup, contribution and security-reporting guides, support expectations, dependency and asset license inventory, required third-party notices, and a reviewed project license. GPL-3.0-or-later was selected for original source on October 13, 2026; LICENSE, COPYRIGHT, package metadata and contribution terms record it. Review actual code reuse, corresponding-source delivery, runtime distribution, fonts, icons, and artwork against the final artifact. Check tracked files and Git history for credentials, personal data, and private-only material before publication. Repository visibility changes require an explicit publication request.

## Implementation sequence

- State integrity, transactional persistence, corruption/downgrade protection, bounded input validation, failure handling, and repeatable Windows CI.
- Real manifest and game-discovery layer; local list import; explicit preflight results.
- Investigate Wabbajack CLI authentication and install invocation against the current upstream build. Use the actual supported interface, rather than guessing CLI flags or hiding an external GUI as a completed integration.
- Installation adapter, durable live jobs, verification, launch and shortcuts.
- Maintenance and release packaging; clean-machine validation and Steam submission materials.
- Open-source release preparation once the application is stable: documentation, licensing/provenance review, notices, contributor guidance, and publication hygiene.

## External release dependencies

Nexus registration requires a working testing build. Valve reviews the product and store presence. Any bundled mods, generated assets/patches, upstream tool components, and branding need suitable distribution rights. These are tracked release gates, not a reason to leave independent implementation work undone.

Sources: [Wabbajack CLI](https://wiki.wabbajack.org/wabbajack_cli/Commands.html), [Nexus API policy](https://help.nexusmods.com/article/114-api-acceptable-use-policy), [Steam review process](https://partner.steamgames.com/doc/store/review_process).

## Work policy

Changes go through feature branches, pull requests, relevant checks and review, then merge to main. Keep progress pushed and review public changes for private operational context and unrelated project material.

## Real-list acceptance finding

[Viva New Vegas acceptance evidence](vnv-acceptance.md) records real game/list/runtime preflight and the remaining authentication and game-preparation gaps. A list engine finishing is not sufficient when the creator requires root-file installation or patching. Model and verify those steps before claiming launch-ready, one-click support; a previously configured game installation cannot establish clean-machine acceptance.

The [Steam submission draft](steam-submission.md) records proposed store copy, claim gates, asset requirements and the reviewer handoff. Its preparation does not close the real acceptance gates above.

## Expanded native release scope (2026-10-13)

The expanded release target adds the following requirements to the original acceptance gates; they are not completed by the 0.2.0 preview:

1. Develop a documented native `.loadstone` format and open implementation from the currently installed TTW, FO3 Remastered and customized New Vegas setups. [Inventory and format direction](installed-inventory.md) defines the first evidence-gathering step. Preserve the live installations and ongoing saves.
2. Implement reproducible native installation, local owned-game reconstruction, source resolution and exact installed-file verification. Assess Wabbajack, Nexus and MO2 interoperability on their actual formats and permissions.
3. Prepare Loadstone-maintained featured lists from those installed versions, including credits, rights-reviewed assets, tested recipes and publication. Distinguish Loadstone's support from endorsement by Bethesda, TTW, Nexus or the original list authors.
4. Target support: Fallout 3 standalone unsupported (defer to TTW); Fallout: New Vegas fully supported; Fallout 4 and Skyrim supported in development; Starfield unsupported but planned. These are product targets; do not mislabel untested paths as release-certified.
5. Investigate paid storage for permitted content. Game ownership and DRM-free delivery alone do not establish rights to operate shared game mirrors. No provider procurement is implied by choosing an architecture.
6. Deliver a reliable 1.0 release candidate for open-source Git distribution and Steam, satisfying the original rights, authentication, clean-machine, installation, maintenance and actual-client gates.
7. Produce release copy/assets, a development roadmap with an appealing visual presentation, and a short application showcase trailer using truthful product footage. Inventory scripts and fixture tests are not substitutes for this media or product acceptance.

Keep this public repository focused on Loadstone implementation, contributor documentation and sanitized release evidence. Private operational coordination and unrelated projects belong outside it. Public source availability does not close the binary-release acceptance gates above.

# Privacy & local data

Canonical source: `docs/privacy.md`

This describes the current source preview, not a future cloud service. Loadstone has no analytics SDK, advertising, automatic crash upload or Loadstone-hosted account service. It does not upload diagnostics automatically.

## Local storage

Packaged app settings and workspace data live in `%APPDATA%\Loadstone`. They include chosen folder paths, imported manifest metadata and source locations, demo state, live installation history, bounded engine output, shortcut locations, and local Steam account identifiers used for saved entries. Test builds can select another app-data directory through `LOADSTONE_DATA_DIR`.

`nexus.bin` contains the key and validated account metadata encrypted through Electron safeStorage/Windows DPAPI. Public status exposes the display name, Premium flag and verification time; the key remains in the main process. Disconnect removes Loadstone's credential files. It does not revoke the provider key or change Wabbajack's account. Same-user software can potentially access credentials; encryption is not a defense against malware in the same Windows account.

Experimental native creator builds store their recipe fingerprint, destination, progress and status in `native-builds.json`. Candidate folders contain their recipe snapshot and reconstruction receipt. The selected private local-inputs JSON remains where you created it; its game/archive paths are read into the main process for the build, not copied into history or sent to the renderer. Native build records are currently excluded from diagnostic exports. Cancelled or interrupted folders remain on disk for review. Confirmed resume retains conflicting files and the previous receipt under `.loadstone-build-recovery/` inside the candidate; these local copies may contain personal configuration and are not automatically deleted or exported. Source inputs must be selected again for each resume review.

Guided native installation does not require that JSON file. Its selected game, prerequisite and archive paths appear locally in the setup screen for review; the main process retains the input map and package path. The draft survives navigation but is discarded on restart, is not persisted or exported, and contains no account credential. Source selections must be made again for recovery. Package import may read Steam installation metadata for game suggestions; it starts no archive downloads.

When a reviewed native build requests original-source downloads, completed archives remain in `native-downloads/` beneath app data for verified reuse. Original hostnames and the cache directory appear in the build review. Signed links, API keys and provider response bodies are not stored in build history or diagnostics. A hard process interruption may leave temporary `.part` files; they are never reused as verified archives. Resetting demo data does not clear this cache.

Installation destinations contain the list snapshot, downloaded archives, MO2 output and engine logs. Steam shortcut backups remain beside Steam's `shortcuts.vdf`. Desktop links point to the installed manager. Resetting demo data does not remove those files or live installations. Library removal retains profiles, saves folders, overwrite files, MO2 settings, downloads and files outside the profile directory in a sibling recovery folder. Other profile files, including custom mods, are deleted only after the removal dialog is accepted. See [removal behavior](installation.md#removing-a-setup) before manually deleting retained data.

## Network activity

Account connection and explicit revalidation contact Nexus Mods. Installation preflight also revalidates access when Nexus downloads are needed. Preparing the engine downloads the pinned official release from GitHub and its download infrastructure. Wabbajack performs list downloads and may contact Nexus, original file hosts and its own supporting services; those providers control their own logging and privacy practices. Local game discovery reads Steam metadata and the Windows Steam registry path. Steam shortcut editing operates on local files.

Explicitly starting a native build with requested downloads contacts the original public HTTPS hosts and their permitted redirect destinations. Uncached Nexus sources trigger account verification and specific file download-link requests; keys go only to the Nexus API. Original providers receive the connection's IP address and Loadstone's application identification. Merely opening Settings or inspecting a native package does not start archive downloads. See [native download handling](native-downloads.md).

## Diagnostics

The Settings export is a structured JSON summary containing app/build identity, platform/runtime versions, preferences, connection status, aggregate demo counts, and up to 25 recent live job summaries. It excludes credentials, account names/IDs, filesystem paths, creator metadata, source URLs and raw logs. Errors are reduced to automatic categories and numeric exit codes; these are triage hints, not diagnoses. The save dialog writes only to the selected local destination and does not upload the report.

Paths, setup names, account display names and local account IDs can identify a user. Review any exported or copied diagnostics before sharing. Loadstone redacts the known API key, query strings and common token fields from captured engine output, but this is not a guarantee that arbitrary third-party output contains no personal data. Native engine logs may be unsanitized during a run or after a crash. Do not share credential files, raw Steam account files or complete user-data folders.

Native library registration stores candidate paths, directory identities, recipe hashes, profile names, save guidance and verification times in local app data. Verification reads candidate files; launching starts its declared MO2 profile. Registration does not contact a server or migrate saves. See [native library behavior](native-library.md) for shortcut and maintenance limits.

Confirmed native removal moves the candidate to a local recovery folder and deletes only reviewed, unchanged recipe files. It retains saves, profile/configuration files, modified files and untracked content; native library state records removal/recovery and shortcut-cleanup status. This preservation policy is separate from Wabbajack removal. See [native maintenance](native-maintenance.md).

Confirmed native repair retains replaced files and the original receipt under `.loadstone-repair-recovery/` inside the registered setup. These copies can contain personal configuration and are not automatically deleted or exported. Existing profiles/configuration are preserved by default; a separate review choice can restore their recipe versions. The local library records repair start/completion, recovery directory and the number of preserved changed files. Source selections remain temporary and must be made again for retry. See [native repair](native-repair.md).

Native version updates show the original version and folder in the temporary guided draft, then record the new candidate in ordinary build history. The two registrations remain independent; no update relationship or personal settings/save transfer is persisted. See [native updates](native-updates.md).

In [manual Nexus download mode](native-manual-downloads.md), opening a file page sends only its public recipe game/mod/file identifiers to the default browser. Browser sign-in and downloads remain in that browser. Loadstone does not receive cookies or NXM/download tokens; its picker verifies the chosen local bytes without uploading them. Verification badges, manual mode and byte progress remain temporary local draft state. No browser protocol associations are installed.

# Security

Canonical source: `SECURITY.md`

Loadstone is under active development. Only current `main` is being developed; there is no supported public stable release or guaranteed response time yet. The published v0.1.0 demo is historical.

This source repository is public. GitHub private vulnerability reporting is not currently enabled, and a monitored confidential contact has not yet been published. Until a private reporting route is listed here, open an issue requesting a private contact without including vulnerability details. Do not post secrets, personal files or exploit details in public issues. Establishing the confidential reporting channel remains a release requirement.

Once a confidential channel is established, include the affected commit/version, Windows version, reproducible steps using synthetic data, expected and observed behavior, and impact in the private report. Do not include Nexus keys, encrypted credential files, personal Steam files, game assets or unreviewed logs. If a credential was exposed, revoke it at its provider rather than relying on deletion from a report.

## Boundaries

The renderer is sandboxed with context isolation and a limited IPC bridge. The main process controls files, credentials and child processes. SHA-256 pins check the engine and imported archive; ownership markers restrict installation recovery and shortcut edits. These controls do not establish that a third-party modlist is trustworthy. Installed mod managers, plugins and games execute as the Windows user. Use trusted creators and original sources.

Windows credential encryption protects against other accounts, not malware running as the same user. Engine log sanitization happens after the child exits; crashes can leave unsanitized native logs. See [privacy](docs/privacy.md) and [installation limits](docs/installation.md).

Version 0.4.0 brings guided native installation and maintenance into an unsigned Windows x64 preview. A local package is not publication or 1.0 acceptance. Preserve the recorded 0.3.0 executable and footage. Build from a clean committed source revision; never label an older artifact with current-source capabilities.

## Build and exercise the artifact

Use Node 24 and pnpm 11 on Windows. Install the locked dependencies, run `pnpm check` and `pnpm test`, then `pnpm notices`. Review and commit any intended notice changes before the final package build. For complete archive coverage, supply `LOADSTONE_TEST_7ZIP` with the trusted tool prepared by `scripts/prepare-sevenzip.ps1`.

```powershell
pnpm package --config.directories.output=release/private-0.4.0
node scripts/steam-depot.mjs release/private-0.4.0/win-unpacked
```

The depot script creates a fresh `release/steam/preview-<id>` containing the entire application, notices, integrity manifest and SteamPipe templates. Verify it with `node scripts/steam-depot.mjs --verify <kit-directory>`. Check its embedded commit, `dirty: false`, version, license, lockfile hash and notice gaps. The lockfile hash uses UTF-8 with CRLF normalized to LF, matching Git archive bytes. No command uploads a depot.

Set `LOADSTONE_TEST_EXE` to the absolute path of that kit's `content/Loadstone.exe`, then run the staged-executable test selection from `.github/workflows/windows.yml`. These tests redirect native side effects to synthetic fixtures; `LOADSTONE_DATA_DIR` alone does not redirect Desktop or Steam operations. Clear `LOADSTONE_TEST_EXE` afterwards.

```powershell
node scripts/verify-portable.mjs release/private-0.4.0 test-results/private-0.4.0
```

This separately exercises the actual portable wrapper, including extraction, current version, renderer/bridge, complete offline GPL and scope texts, settings, demo isolation and clean shutdown. Inspect its screenshots and JSON evidence. Preserve its SHA-256 and size along with the unpacked depot inventory. Neither check certifies real games, real accounts or the actual Steam client.

## Exact source and review material

Read the **embedded build commit** from the verified depot manifest. From the source repository, use that exact commit, not a subsequently merged branch tip:

```powershell
git -c core.autocrlf=false -c core.eol=lf archive --format=zip --prefix=Loadstone-source/ --output=release/private-0.4.0/Loadstone-0.4.0-source.zip <embedded-build-commit>
```

The explicit Git settings preserve LF source bytes independently of Windows checkout defaults. The archive must contain all tracked build inputs, including original source, lockfile, scripts, tests, license/scope, notices and documentation. Inspect the ZIP inventory and every archived file against that Git tree. Exclude Git history, installed dependency trees, raw acceptance evidence, credentials, game files and mod downloads. Rebuild from an extracted source archive with `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm test` and `pnpm package`; without Git metadata the build identity deliberately reports an unknown commit.

Keep a local review manifest linking the executable and source ZIP hashes, exact build commit/tree and lockfile hash, depot inventory, test evidence and tool versions. Build/test dependencies are fetched from the locked upstream graph; they are not bundled in this source ZIP. # Steam packaging

Canonical source: `docs/steam-release.md`

`pnpm package:steam` generates a Windows x64 **directory build**, distinct from the self-extracting portable EXE. It stages a new kit under `release/steam/preview-<id>/` without replacing existing kits. This is a private developer preview, not a submitted or approved Steam build.

The kit contains:

- `content/`: the complete Electron application and runtime, including Electron/Chromium and Loadstone dependency notices. The depot must include this entire directory.
- `depot-manifest.json`: source commit, dirty-worktree flag, lockfile hash, application version, launch settings and SHA-256/size for every content file. No build-machine paths are embedded in this manifest.
- `scripts/`: SteamPipe app/depot templates. Replace the two ID placeholders with assigned Steamworks IDs and rename both files to `.vdf`.
- `README.txt`: operator instructions and outstanding release gates.

Build with Node 24 and pnpm 11 from a clean checkout after `pnpm install --frozen-lockfile`, `pnpm check`, and `pnpm test`. A dirty build is identified as dirty, never silently certified. The file inventory is for integrity and provenance; binaries are not claimed to be byte-reproducible or signed. A matching inventory also does not prove absence of secrets or compliance with licenses.

```powershell
pnpm package:steam
node scripts/steam-depot.mjs --verify release/steam/preview-<id>
$env:LOADSTONE_TEST_EXE = (Resolve-Path 'release/steam/preview-<id>/content/Loadstone.exe').Path
node --test tests/electron.test.mjs tests/live.test.mjs tests/nexus.test.mjs tests/onboarding.test.mjs tests/close-guard.test.mjs
Remove-Item Env:LOADSTONE_TEST_EXE
```

To generate preview scripts with assigned IDs directly, run `node scripts/steam-depot.mjs release/steam-unpacked/win-unpacked <app-id> <depot-id>`. This stages a fresh kit. No helper invokes SteamCMD, logs into Steam, uploads content or changes a branch. Templates set `Preview` to `1` and omit `SetLive`; [Valve documents this mode](https://partner.steamgames.com/doc/sdk/uploading) as generating logs and manifests without upload. The Steamworks SDK, account and IDs are supplied separately by the maintainer.

## Steamworks setup and acceptance

Configure the launch executable as `Loadstone.exe`, Windows 64-bit, with no launch arguments and the application root as working directory. Map `content/` as the Windows depot root. Do not point Steam at the portable self-extracting wrapper. Do not bundle `depot-manifest.json`, SteamPipe scripts, upload credentials, user data, downloaded engines, or game/mod archives.

Settings, protected Nexus credentials and installation history stay in Electron's per-user app-data directory, outside the depot. Installed setups and recovery folders belong outside the application directory. Do not configure Steam Cloud for credential files. Test updates and uninstall through the actual Steam client to confirm user data and external setups remain intact; local Electron tests cannot establish Steam behavior.

Before upload or review, verify GPL-3.0-or-later corresponding-source delivery and all shipped notices, finalize asset licensing and Nexus registration, supply a permitted real creator list, complete clean Windows install-to-play acceptance, review public claims/screenshots, and configure support/privacy links. Local-only packages need no Wabbajack engine or Nexus connection; optional Wabbajack setups have a separate manifest import and engine configuration. Existing schema-1 workspaces migrate to schema 2 with their selected mode and preferences retained.

[Valve's review process](https://partner.steamgames.com/doc/store/review_process) covers the actual store presence and build. Successful packaging or fixture checks do not establish acceptance by Valve. No Steam depot has been uploaded. A partial [real TTW shortcut/launch check](native-steam-acceptance.md) reached the menu after an edition prompt; the revised candidate's direct launch failed before the menu. No gameplay or recording acceptance is claimed. These non-Steam-shortcut checks do not test installing or updating the Loadstone depot through Steam.
