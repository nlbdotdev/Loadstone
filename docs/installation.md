# Live installation preview

Disable dummy data in Settings, prepare the pinned engine, connect a Nexus account if the list requires it, then import a creator manifest with its original Wabbajack archive. Check compatibility in Discover. Installation becomes available only after all checks pass; starting repeats the checks. Wabbajack must resolve the same game folder selected in Loadstone. Lists requiring unsupported providers or manual Nexus downloads are blocked.

Only one live installation runs at a time. Downloads displays actual engine output and job phases, without estimating a percentage from elapsed time. Library entries appear only after the engine exits successfully, structural profile verification passes, and the declared output files are checked. Structural checks cover the manager executable, configuration, declared profile and launch target. Output checks revalidate the owned list archive SHA-256, require every final declared file to be a regular file within the profile, reject redirected paths, and compare sizes for InlineFile, FromArchive and PatchedFromArchive outputs. INI files, modlist.txt, remapped and other generated outputs receive presence/path checks because their content may legitimately change. Temporary BSA inputs are excluded when the list declares CreateBSA outputs; the final BSA files are still required.

The pinned [upstream installer](https://github.com/wabbajack-tools/wabbajack/blob/4.2.3.0/Wabbajack.Installer/StandardInstaller.cs) rewrites configuration and removes [temporary BSA inputs](https://github.com/wabbajack-tools/wabbajack/blob/4.2.3.0/Wabbajack.Installer/Consts.cs). Output verification records its checked counts and completion time; Library shows these as installation-time evidence, not a continuous integrity guarantee. A missing file or size mismatch leaves the job failed and retryable. Cancellation during verification also remains retryable. The checks do not establish installed-file checksum integrity or gameplay correctness, and existing installations are not retroactively labeled verified.

## Launching

Library offers **Launch setup** and **Check profile**. Launch repeats structural checks, requires the original `portable.txt` marker, and rejects a redirected MO2 profile directory. It invokes the installed manager with `-p <profile> run -e <configured executable title>` as separate process arguments, using the manager directory as its working directory. No shell interprets titles or paths, and inherited Nexus credential variables are removed. This adapter targets MO2's standard portable layout and the command interface present in [MO2 2.5.2](https://github.com/ModOrganizer2/modorganizer/blob/v2.5.2/src/commandline.cpp). The [portable marker behavior](https://github.com/ModOrganizer2/modorganizer/blob/v2.5.2/src/instancemanager.cpp) keeps instance selection local.

Status tracks the spawned manager process, not gameplay or playtime. MO2 may hand the request to an existing window; check that window for game startup or errors. Closing Loadstone leaves the manager/game running. Manager tracking is session-local and does not survive a Loadstone restart.

## Steam library entries

Library offers **Add or repair Steam entry**, with explicit local-account selection. Steam must be fully closed; Loadstone checks for Steam processes twice and never closes Steam itself. With the Steam shortcut preference enabled, installation attempts automatic creation only when one local account is available. If Steam is running, no account exists, or account selection is ambiguous, installation remains successful and the library reports the follow-up needed.

Entries target the same portable MO2 command as desktop shortcuts. The updater understands the binary KeyValues format used by `userdata/<account>/config/shortcuts.vdf`. It preserves unrelated entries as their original bytes and preserves the app ID and additional fields when repairing a matching Loadstone entry. A per-installation tag identifies ownership. Name/app-ID conflicts, malformed or unsupported data, redirected files and concurrent file changes stop the edit. Existing files receive a uniquely named `.loadstone-<id>.bak` backup before replacement. To restore one, exit Steam and copy the desired backup over `shortcuts.vdf`; this restores the entire previous shortcut library.

This is a local-file integration, not a public Steamworks shortcut API. Format references: [ValvePython's binary KeyValues implementation](https://github.com/ValvePython/vdf) and [SteamTinkerLaunch's shortcut integration](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Add-Non-Steam-Game). Tests use isolated Steam directories. Read-only inspection of the development machine's existing three-entry shortcut file confirmed an exact binary round trip. Creating an entry and launching it from the actual Steam client still needs release acceptance testing; neither the tests nor this inspection changed that real shortcut file.

## Desktop shortcuts

When the desktop shortcut preference is enabled in Settings, successful installation creates a Windows `.lnk` on the user's Desktop. Library also offers creation and repair. Creation repeats launch checks, quotes each Windows argument, writes a temporary link through [Electron's native shortcut API](https://www.electronjs.org/docs/latest/api/shell/), reads it back for verification, and then publishes it. The target is the installed MO2 executable, with the same profile, configured launch title and working directory as library launch. The shortcut works without Loadstone open; it therefore does not repeat Loadstone's checks when double-clicked.

Each filename and description includes the installation ID. Repair recreates a missing link or replaces the matching owned link. It refuses to overwrite a link with a different ownership description. Shortcut errors appear separately and leave a successful installation installed. The displayed path records the last successful creation; it is not a continuously checked existence indicator. Tests use a temporary Desktop folder and real Windows shortcut read/write calls, leaving the user's Desktop untouched.

## Owned files and recovery

The selected destination must initially be empty. Loadstone records an ownership marker and creates `profile/` for Wabbajack output, `downloads/` for reusable archives, `work/` for the engine working directory, and a hashed `list.wabbajack` snapshot. Retry requires matching ownership and preserves downloads and partial output. It also repeats preflight against the imported manifest and source archive; keep those available. Changed source manifests may prevent a retry of the original snapshot.

Cancel stops the tracked engine process tree. Completion is recorded only after the child exits. An unexpected app interruption leaves a durable job that becomes interrupted on reopening. Restart Windows before retrying that job: the saved Windows boot identifier prevents reuse while the previous engine might still be running. Loadstone does not automatically restart interrupted work.

## Credentials and diagnostics

The main process passes the private-test Nexus key only to the engine environment. Renderer job history contains no key. Captured output redacts the exact key, URL queries and named token fields, retaining at most 150 lines of 1,000 characters each. After the child exits, matching Wabbajack CLI logs in the owned working directory are sanitized; oversized logs are replaced with a short notice. Native engine logs may remain unsanitized while installation is running or after a crash. Do not publish raw engine logs without reviewing them. Third-party diagnostics outside that working directory are not covered by this sanitizer.

## Removing a setup

**Remove setup** checks ownership and scans the installed profile before presenting a native confirmation dialog with the exact destination, recovery folder, file count and estimated file bytes to remove. Supported game, script extender, MO2 and Wabbajack processes must be closed. Loadstone will not stop them automatically. Junctions and symbolic links anywhere inside the profile block removal, as do overlaps with game, system or application folders.

On confirmation, Loadstone records durable removal state and moves the owned destination to a sibling folder named `<destination>.loadstone-recovery-<installation-id>`. It deletes ordinary installed files inside `profile/` while retaining all of `profile/profiles/`, `profile/overwrite/`, `ModOrganizer.ini`, and any directory named `saves`. Downloads, the list archive, engine logs and other files outside `profile/` remain in the recovery folder. Global saves outside the setup are untouched. Custom mods and other files inside `profile/` outside the retained locations are deleted; copy anything else you want to keep before confirming.

No recursive deletion follows reparse points. Each file is checked again before deletion. If a file is locked or the app closes, the job becomes resumable removal work; **Resume removal** repeats the checks and continues. A completed removal leaves the library and stays in Downloads history with its recovery location. The original destination can be used for a fresh installation. The retained data is not a full restore of deleted mods; transferring saves to another list requires that creator's save-compatibility guidance.

After removal, Loadstone deletes its matching desktop link and tagged Steam entries across available local accounts. Unrelated shortcuts are retained. Steam must be closed for any Steam file edit; each edit gets a backup and preserves remaining entry fields and app IDs, renumbering entry indices where necessary. Cleanup failures leave the setup removed and show **Clean up shortcuts** in Downloads for retry, including after restart. Renamed desktop links and unavailable Steam accounts may require manual cleanup. Version updates use separate fresh installations with creator-declared save guidance; see [updating manifests](manifests.md#updating-an-imported-setup). The previous setup remains available until explicitly removed. Deleting the recovery folder would delete the retained saves and downloads, so Loadstone does not purge it automatically.

## Verification status

Tests exercise real child processes with synthetic files: success, failure, cancellation, retry, ownership rejection, restart recovery, credential redaction, launch arguments, duplicate launch prevention and manager exit handling. Electron tests cover library profile checks and demo-mode launch rejection. The pinned official engine has separately passed integrity, version, help and game discovery checks. A full real list download, install and play session has not yet passed acceptance testing. These source features are newer than the v0.1.0 portable preview.
